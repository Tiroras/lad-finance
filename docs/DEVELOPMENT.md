# Проверки и ведение документации

Обязательные проверки по типу изменения выбираются по [AGENTS.md](../AGENTS.md#запуск-и-проверка-изменений). Здесь описаны условия запуска, работа с результатами и документацией. Читайте разделы, относящиеся к текущей задаче.

## Режимы и данные для проверок

Перед запуском выберите режим и зафиксируйте его в результате. Значения определяются в [buildOptions.ts](../src/shared/lib/buildOptions.ts); опцию включает только строка `true`.

| Режим                 | Опции и поведение                                                                                                                                          | Когда использовать                                                        |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| Дефолтный (`default`) | `EXPO_PUBLIC_ENABLE_DEMO` и `EXPO_PUBLIC_RESET_ON_START` выключены. Загружается сохранённый учёт; первый вход создаёт пустой личный профиль                | Личный учёт, сохранение между запусками, отсутствие демофункций           |
| Демо (`demo`)         | `EXPO_PUBLIC_ENABLE_DEMO=true`, очистка выключена. Доступен отдельный профиль «Демо»                                                                       | Заполненные экраны, аналитика, прогноз и сценарии с примерами             |
| Фреш (`fresh`)        | `EXPO_PUBLIC_RESET_ON_START=true`, демо по умолчанию выключено. В разработке новый запуск JS или полный Reload очищает все профили и открывает приветствие | Первый вход, обучение и пустые состояния на изолированных тестовых данных |

Команды запуска и экспорта: [обычный запуск](../README.md#запуск), [Demo](../README.md#деморежим-по-явной-опции), [Fresh](../README.md#запуск-с-нуля). В Demo явно выбирайте профиль «Демо»: опция не заполняет личный профиль и не пропускает приветствие.

Проверяйте обе опции в окружении и `.env*`: обычные команды Expo наследуют их. После смены режима перезапускайте Metro и делайте полный Reload; готовое приложение нужно пересобрать. Demo и Fresh можно совместить явно, если нужны чистый запуск и доступный демопрофиль.

Fresh удаляет весь локальный учёт без резервной копии. Обычный Fast Refresh очистку не повторяет. В release Fresh отключён условием `__DEV__`, команды `build:fresh` нет. Для проверки сохранения после перезапуска нужен default или Demo с выключенной очисткой.

## Модульные и браузерные проверки

- Проверяйте наблюдаемое поведение, точные суммы и даты, сохранность данных и отсутствие повторного учёта. Не копируйте реализацию расчёта в тест ради совпадающего результата.
- Для проверки дат фиксируйте `today` в модульных тестах и часы браузера в Playwright. Используйте отдельный браузерный контекст с тестовыми данными.
- Playwright использует локаль `ru-RU`, часовой пояс `Europe/Samara` и разные серверы для режимов:

| Режим   | Команда                     | Адрес                   | Переиспользование сервера                     |
| ------- | --------------------------- | ----------------------- | --------------------------------------------- |
| Demo    | `npm run test:e2e:demo`     | `http://localhost:8087` | Локально допустимо, в CI — собственный сервер |
| Default | `npm run test:e2e:personal` | `http://localhost:8089` | Локально допустимо, в CI — собственный сервер |
| Fresh   | `npm run test:e2e:fresh`    | `http://localhost:8093` | Всегда отдельный сервер                       |

`npm run test:e2e` последовательно выполняет все три набора. Переиспользуемый сервер должен иметь нужную демоопцию и выключенную очистку. Не останавливайте чужой сервер ради теста.

При установленном Chrome используйте `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`. Иначе установите браузер через `npx playwright install chromium`. Конфигурации: [Demo](../playwright.config.ts), [default](../playwright.personal.config.ts), [Fresh](../playwright.fresh.config.ts).

## Мобильные проверки и Docker

Перед нативным запуском прочитайте [инструкцию мобильного CLI](../README.md#мобильные-тесты-из-терминала-ide) или [DOCKER.md](DOCKER.md), в зависимости от окружения. Для интерактивной проверки используйте Maestro MCP, если он подключён: сначала получите список устройств и явно выберите нужный эмулятор. Подготовка MCP и предусловия сценариев описаны в [MAESTRO_AGENTS.md](MAESTRO_AGENTS.md).

- `npm run test:mobile -- path/to/flow.yaml` собирает актуальный Android release с выключенной очисткой. Для Demo задайте `EXPO_PUBLIC_ENABLE_DEMO=true` перед командой. Fresh этим способом не включается.
- В обоих CLI требуется существующий файл или папка сценариев нужного режима. Без пути команда завершается до подготовки устройства и сборки; папка запускает только YAML верхнего уровня, без рекурсивного обхода.
- `--no-build` использует режим уже установленной сборки. После изменений продукта или смены режима выполняйте сборку заново.
- Docker поддерживает Fresh через debug-сборку и отдельный Metro. Подготовка интерактивного MCP отличается от CLI-теста: сервер, поднятый для одного теста, останавливается после него. Используйте инструкции выбранного способа запуска.
- Не смешивайте локальные пути с `/workspace/` в контейнере и не запускайте два исполнителя на одном устройстве. Эмулятор работает на компьютере, а не внутри контейнера.

Воспроизводимые сценарии размещайте в `tests/mobile/<mode>/`; общего smoke нет. Перед запуском существующего сценария читайте его план и соблюдайте режим, дату и подготовку данных. Точные условия `demo/refactoring.yaml` находятся в [плане](../tests/mobile/plans/refactoring.md#реализованный-сценарий-и-подготовленная-сборка). Порядок работы ролей planner → generator → healer и правила разбора падений остаются в [MAESTRO_AGENTS.md](MAESTRO_AGENTS.md).

## Экспорт и CI

Для изолированного экспорта без сети:

```sh
EXPO_OFFLINE=1 npx expo export --platform all --max-workers 2
```

Проверка совместимости зависимостей в offline-режиме использует локальные сведения SDK. Экспорт не создаёт установочный APK/IPA; для системного поведения нужна нативная проверка.

[CI](../.github/workflows/ci.yml) выполняет TypeScript, модульные тесты, проверку зависимостей, экспорт и Playwright. Отдельной команды `lint` нет. Команды общих проверок через Docker и сборки APK без сценария описаны в [DOCKER.md](DOCKER.md).

## Актуализация документации

Обновляйте документ по его ответственности, сохраняя единственное подробное описание каждого правила:

| Документ                                              | Ответственность                                                     |
| ----------------------------------------------------- | ------------------------------------------------------------------- |
| [README.md](../README.md)                             | Запуск и пользовательский обзор                                     |
| [FEATURES_CURRENT.md](FEATURES_CURRENT.md)            | Реализованные функции, ограничения и матрица подтверждений          |
| [ARCHITECTURE.md](ARCHITECTURE.md)                    | Размещение файлов, зависимости и композиция приложения              |
| [COMPETITORS.md](COMPETITORS.md)                      | Продуктовые решения и сравнение возможностей                        |
| [LEARNING_TOUR.md](LEARNING_TOUR.md)                  | Экскурсия через настоящие экраны приложения                         |
| [VERIFICATION.md](VERIFICATION.md) и связанные отчёты | Фактические результаты проверок и их пределы                        |
| Тематические документы `docs/`                        | Подробные правила прогноза, валют, импорта, защиты и других функций |

При изменении функции, режима запуска, формата данных, защиты или ограничения обновляйте затронутый раздел `FEATURES_CURRENT.md` в той же задаче. Указывайте дату сверки и базовый коммит; без смысловой правки дату не обновляйте. Планы разработки не записывайте как готовые функции.

Сохраняйте матрицу «функция — платформа/способ проверки — дата/версия — результат и предел». Источник подтверждения — реальный протокол в `VERIFICATION.md` или связанном отчёте. Неизвестный SHA запуска отмечайте явно; исторический отчёт не переписывайте как проверку текущей версии. Критерии оформления протокола — в [правилах отчётов](tasks/2026-10-06-follow-up/reports/README.md).

При изменении обучения согласуйте шаги, подсветку, тексты и переходы в `LEARNING_TOUR.md`, коде и проверках. Сохраняйте прохождение через настоящие экраны приложения.

## Ведение задач

Для [очереди follow-up](tasks/2026-10-06-follow-up/README.md) порядок реализации, уточнения пользовательского запроса, словарь статусов и зависимости ведутся в индексе и карточках. Конкретные ID, текущие статусы и приоритеты не дублируются в корневой инструкции.

- При начале работы, изменении объёма, блокере и завершении обновляйте карточку и строку индекса вместе. Сохраняйте время создания, обновляйте `Обновлено` в ISO 8601 со смещением UTC и добавляйте датированную запись в журнал. Время старого замечания нельзя восстанавливать по mtime файла.
- Если пункт требует анализа, до реализации запишите варианты, выбранный вариант и основание в карточке или `analysis/`. Рутинные решения в разрешённом объёме принимайте самостоятельно; уточняйте существенную неоднозначность. Новые финансовые правила согласуйте с действующими инвариантами и совместимостью данных.
- Поле `Анализ` ведите отдельно от статуса реализации; согласуйте его с [итогами аналитического этапа](tasks/2026-10-06-follow-up/analysis/README.md). Методика измерений не заменяет фактические замеры, а готовая записка не означает внедрение предложенных функций. Не расширяйте аналитическое поручение до реализации без основания в запросе пользователя.
- `done` допустим после выполнения критериев задачи, необходимых проверок и обновления документов. Запишите, что выполнено, время завершения и ссылки на доказательства. Частичную работу не закрывайте целиком: перечислите оставшиеся пункты. Для аналитической задачи результатом может быть готовая записка, если это соответствует критериям.
- Результаты прогонов храните в `reports/` по [правилам отчётов](tasks/2026-10-06-follow-up/reports/README.md), со ссылкой из карточки и при необходимости `VERIFICATION.md`. Укажите режим, платформу/устройство, сборку, команду, дату, результат и ограничения. Недоступную проверку помечайте `not-run` с причиной.
- Исходный [реестр замечаний](thesis/remarks-2026-10-06.md) и Word-версия остаются историческим срезом. Оперативные статусы ведите в очереди задач, сохраняя исходные ID и даты; учитывайте уточнения объёма из индекса.

## Снимки и артефакты

Для снимков используйте `scripts/capture-features.mjs`, `scripts/capture-forecast.mjs` и `node --import tsx scripts/capture-planning.mjs` при работающем сервере на 8087. Подготовьте режим и данные, ожидаемые скриптом; первые два используют демопримеры. `scripts/capture.mjs` также перезаписывает иконки приложения — учитывайте этот побочный результат перед запуском.

`docs/screenshots/` очищена по просьбе пользователя и исключена из Git; создавайте снимки только для проверки. Валютные e2e сохраняют их в `test-results/`. Генерируемые `dist/`, `.expo/`, `test-results/`, `playwright-report/`, `ios/`, `android/` также исключены из Git и не должны попадать в коммит как побочный результат проверки.
