# Защита данных Лада

## Нативное хранилище

После перехода на Expo SDK 58 файловый адаптер ожидает завершения каждой асинхронной записи и чтения части перед закрытием файла и проверкой поколения. Порядок фиксации, форматы конвертов и размещение ключей сохранены. Модульные проверки используют отложенные файловые операции; результаты обновления и пределы нативной проверки — в [отчёте SDK 58](VERIFICATION.md#expo-sdk-58--25-октября-2026-года).

На iOS и Android записи шифруются AES-256-GCM через Expo Crypto. Каждое сохранение использует новый случайный IV; GCM проверяет целостность шифротекста, а дополнительные аутентифицированные данные связывают его с форматом и ID ключа. ID встроенных профилей — `personal` и `demo`, дополнительных — `profile-<UUID>`. JSON-конверт с версией, ID ключа и base64 от IV, шифротекста и тега записывается в отдельный файл постоянного каталога приложения `lad-ciphertext-v1/<id>/`. Открытый финансовый JSON в этот каталог не записывается.

Прежний ключ AsyncStorage `lad-profile-<id>:lad-finance-encrypted-v1` теперь содержит небольшую ссылку на конкретное поколение файла: формат, версию, ID профиля и ключа, безопасное имя, длину и SHA-256. Это открытые служебные данные без финансовых записей. Так большие конверты не проходят через ограничение одной строки Android CursorWindow и общий предел старого AsyncStorage. Исторический конверт непосредственно в AsyncStorage читается без переноса; следующий успешный save записывает файл и заменяет эту строку ссылкой. Проверка `inspect()` ничего не переносит и не удаляет.

[Протокол записи](../src/infrastructure/storage/encryptedFileStorage.ts) создаёт новое поколение, закрывает файл и перечитывает его целиком до публикации ссылки. Затем проверяются опубликованная ссылка и полный файл; только после этого можно удалить предыдущее поколение. Неопределённый результат записи или чтения оставляет оба файла. Повреждённая ссылка, отсутствующий файл или несовпадение отпечатка вызывают ошибку, без возврата к старому снимку. Файл без опубликованной ссылки может быть результатом прерывания до фиксации: его не выбирают автоматически по дате и не удаляют при сканировании профилей. Каталог профилей восстанавливается по прежним логическим ключам. Закрытие и обратное чтение проверяют результат записи в работающей ОС; это не обещание сохранности при физическом отключении питания. Нативная приёмка изменения описана отдельно в [отчёте T02](tasks/2026-10-06-follow-up/reports/T02-native-recovery.md).

Физическое чтение файла ограничено 64 000 000 байт до выделения буфера. Этот предел не меняет финансовые лимиты: для нормализации версии 1 консервативный максимум конверта — 46 690 644 байта. Нормализованный снимок ограничен `4 × 5 000 000 + 200 × 24 + 15 + 1 = 20 004 816` байтами: канонизация существующих JSON-токенов, добавление `startsOn` не более чем 200 платежам, пустого `scenarios` и смена признака demo. Вместе с исходником до 15 МБ, служебным заголовком, AES-GCM и base64 это укладывается в указанный максимум. При изменении нормализации или пределов схемы расчёт нужно пересмотреть.

Случайный ключ каждого профиля хранится отдельно через Expo SecureStore: iOS Keychain с `WHEN_UNLOCKED_THIS_DEVICE_ONLY`, Android Keystore. Имена ключей и `keychainService` разделены по профилям. Ключ не входит в экспорт. Данные и ключ могут находиться в памяти работающего приложения; блокировка интерфейса не обещает защиты от взломанной ОС, инструментирования процесса или доступа к памяти.

Список профилей `lad-profiles-v1` содержит только их ID и названия, а `lad-active-profile-v1` — последний выбранный ID. Эти служебные данные хранятся в AsyncStorage без шифрования. Используйте нейтральные названия профилей: имя не защищено шифрованием финансового снимка. У каждого учёта отдельные финансовые записи и история копий. Профили не являются отдельными пользователями с разграничением доступа.

Повреждённый список вызывает ошибку загрузки и не заменяется пустым. Отдельная проверка сохранённых пространств профилей читает записи без миграции, создания ключей или удаления источника. Недоступный ключ означает «пока недоступен», а не отсутствие учёта. Список восстанавливается только после подтверждения. Служебный журнал хранит ID операции, прежний и кандидатный список, стадию и проверочные метаданные без финансового JSON, пароля или ключа; эти метаданные также открыты. После прерывания продолжается та же операция. Возврат прежнего списка не удаляет финансовые снимки. Это согласованный порядок проверяемых записей, а не транзакция между AsyncStorage и SecureStore.

Прогресс обучения `lad-learning-progress-v1` общий для приложения и хранится в AsyncStorage без шифрования. Формат версии 2 содержит только версию, состояние прохождения и идентификатор текущего шага экскурсии. Имена, финансовые суммы, операции и черновики форм в него не попадают. Прежний формат читается с переходом на начало нового маршрута. Запись проверяется при чтении; повреждённые учебные метаданные сбрасываются, не затрагивая финансовые данные. Ошибка доступа к хранилищу позволяет повторить загрузку или сохранение обучения. Прогресс не входит в финансовые копии; запуск с нуля очищает его вместе с остальными записями приложения.

Профили используют новые пространства ключей. При обычном запуске прежние общие `lad-finance-v1`, `lad-finance-encrypted-v1` и их ключи SecureStore не читаются, не переносятся и не удаляются. Это явный переход к новым пустым профилям; отдельного экрана прежних данных нет.

Для разработки есть отдельный [запуск с нуля](../README.md#запуск-с-нуля): `npm run start:fresh` / `npm run web:fresh`. Только при `__DEV__` и точном `EXPO_PUBLIC_RESET_ON_START=true` перед загрузкой провайдеров удаляются локальные записи с префиксом `lad-`, собственный каталог зашифрованных поколений (включая неопубликованные), распознаваемые ключи SecureStore, разрешения большого восстановления, настройка блокировки и напоминания «Лада». ID ключей извлекаются из конвертов, ссылок, имён поколений и разрешений восстановления, без чтения больших файлов. Удаление файлов всегда ограничено собственным каталогом, а не путём из входных метаданных. Это явная очистка всех профилей, включая прежнее общее хранилище, без создания копии и подтверждения в интерфейсе. Ошибка останавливает запуск и позволяет повторить очистку. В релизном пакете флаг не действует.

Внутри пространства одного профиля адаптер сохраняет поддержку открытой записи `lad-finance-v1`: сначала валидирует её, записывает зашифрованную копию, проверяет обратное расшифрование и чтение конверта, затем удаляет открытый источник только этого профиля. При наличии зашифрованного конверта повреждение или отсутствие ключа вызывает ошибку: автоматического возврата к открытой копии нет. Ошибка очистки также отображается, и очистка повторяется при следующем чтении/сохранении. Другой профиль и внешние резервные копии не затрагиваются.

## Блокировка

В разделе **Профиль → Защита данных** можно включить блокировку Face ID / Touch ID / Android-биометрией с допустимым системным кодом устройства. На Android запрашивается сильная биометрия. Включение и выключение требуют системной проверки. Настройка общая для приложения, хранится отдельно от финансового JSON и не меняется при переключении профилей, импорте или сбросе учёта.

При запуске данные не загружаются до первого подтверждённого входа, если блокировка включена. При потере активности содержимое скрывается и вход закрывается. Системный диалог аутентификации не запускает блокировку повторно; отмена или уход в фон во время проверки не открывает приложение. Черновик открытой формы сохраняется под блокирующим экраном. iOS использует системную защиту предпросмотра приложения, Android — `FLAG_SECURE` через Expo ScreenCapture, включая запрет скриншотов при включённой блокировке.

Блокировка — проверка доступа к интерфейсу. Ключ шифрования не привязан к текущему набору биометрии (`requireAuthentication` для ключа не используется), поэтому добавление отпечатка не инвалидирует его автоматически. Надёжность кода и биометрии определяется настройками устройства. Face ID не работает в Expo Go: требуется собственная нативная сборка.

## Копии и восстановление

Экспортируемые JSON и `.ladrescue` **не зашифрованы**. Они предназначены для переноса и аварийного восстановления; храните их в защищённом месте. Копия содержит финансовые данные только выбранного профиля, без списка профилей и их названий. Для обычной копии доступны явная замена выбранного профиля и восстановление в новый личный профиль; большой архив восстанавливается только в новый профиль. Прежние профили не удаляются при создании нового.

Каждый нативный экспорт использует свой временный каталог; одновременные выгрузки с одинаковым именем файла не используют общий файл. Каталог удаляется после завершения или ошибки системного обмена. При импорте приложение читает выбранную кэш-копию по ограниченным диапазонам. Пока ожидается пароль или повтор ввода после отказа, выбор остаётся открытым; завершение, отмена, смена выбора или закрытие формы освобождают его. Исходный пользовательский файл не удаляется. Web использует части `File`/`Blob`, без неограниченного `fetch` как запасного пути.

Дополнительно можно создать переносимую копию `.ladbackup` с отдельным паролем. Она содержит весь финансовый JSON версии 4–8. Версия 5 используется для архива счетов и статусов операций, версия 6 — для истории условий платежей, доходов и бюджетов, паузы и переноса/отмены отдельных поступлений; версия 7 — для графиков целей, циклов и освобождений годовых фондов, дат подтверждения и напоминания об обновлении кредитных условий; версия 8 — для назначений счетов и плановых переводов прогноза, оснований исторических оценок, активности строк сценария и счёта разового события. Копии финансовых версий 1–4 читаются с прежней нормализацией в версию 4, версии 5–8 проверяются отдельно. Ключ устройства и настройка биометрии в неё не входят. Формат защищён AES-256-GCM, ключ 32 байта получается из точного UTF-8 пароля через PBKDF2-HMAC-SHA256 с 600 000 итераций. Каждая копия получает новую случайную соль 16 байт и nonce 12 байт; тег — 16 байт. На телефоне случайные байты получаются через `getRandomValues`, без отладочного fallback `getRandomBytes`.

Чтение прежних копий не добавляет массивы версий и не меняет прежнюю нормализацию: исходные условия рассматриваются как виртуальная версия до первого действия с историей. История планов повышает финансовый формат как минимум до 6; графики целей, фонды и подтверждение либо напоминание о кредитных условиях — до 7. Новая семантика прогноза, оценки и сценария повышает формат до 8; последующие действия его не понижают. Чтение версий 5–7 сохраняет прежние данные без новых полей, сегодняшней даты неизвестной оценки или сохранённого признака активности строки сценария. Поля формата 8 под номером прежней версии отклоняются. Неизвестные обязательства ранее выключенного плана не восстанавливаются. Проверка копии контролирует интервалы условий, ссылки событий на свои версии, отсутствие повторов и целостность связанных записей фонда; ошибка отклоняет копию целиком. Версия финансового JSON не меняет версию шифрованного конверта или большого архива. Пределы размеров остаются прежними.

JSON-конверт версии 1 содержит фиксированные имена формата, шифра и KDF, число итераций, соль и hex от `nonce || ciphertext || tag`. AAD связывает формат, версию, шифр, параметры KDF и соль. Неизвестные параметры и превышение размера отклоняются до вычисления ключа. После расшифрования выполняется обычная полная проверка финансового JSON. Неверный пароль и подмена файла не меняют хранилище.

### Большой архив версии 2

Обычные лимиты не повышены: новый обычный JSON ограничен 5 000 000 байт UTF-8, парольный JSON-конверт версии 1 сохраняет прежние пределы. Для старого допустимого исходника, выросшего после нормализации или ещё не уменьшенного до обычного предела, используется отдельный двухраздельный архив. Он хранит неизменяемый исходный JSON и точный текущий финансовый снимок. Последующие изменения не заменяются прежним исходником при экспорте.

Формат [rescueArchive.ts](../src/infrastructure/crypto/rescueArchive.ts): ASCII `LADRESC2` (8 байт), 4-байтная длина заголовка big endian, JSON-заголовок UTF-8 не больше 2 048 байт, затем разделы `source` и `snapshot`. Заголовок содержит ровно `format: "lad-rescue-archive"`, `version: 2`, `protection`, `normalizationVersion: 1`, `normalizationDate`, `snapshotDate`, `sourceBytes`, `snapshotBytes`. Даты — календарные `YYYY-MM-DD`; размер раздела включает его криптографические накладные данные, если защита включена. Версия финансового JSON остаётся отдельной от версии архива.

При `protection: "none"` разделы содержат открытый UTF-8, расширение — `.ladrescue`. При `protection: "password"` файл имеет расширение `.ladbackup`; заголовок дополнительно содержит `cipher: "AES-256-GCM"`, `kdf: "PBKDF2-SHA256"`, `iterations: 600000`, `salt` из 32 строчных hex-символов. PBKDF2 вычисляется один раз на архив с новой 16-байтной солью. Разделы шифруются тем же 32-байтным ключом с разными случайными 12-байтными nonce; совпавшие nonce отклоняются. Каждый раздел записан как `nonce || ciphertext || tag`, тег 16 байт. AAD каждого раздела — точные первые 12 байт файла, точные байты заголовка и UTF-8-строка `/lad-rescue-archive/2/source` либо `/lad-rescue-archive/2/snapshot`. Это связывает обе части с заголовком и их назначением; перестановка разделов, подмена даты, соли или содержимого не проходит аутентификацию.

Reader сначала проверяет ограниченный заголовок, точный общий размер и исходный раздел: не больше 15 000 000 байт UTF-8, после декодирования — 5 000 000 единиц UTF-16. Проверенный исходник нормализуется с указанной датой/версией; точные длины результата измеряются до выделения его полного буфера. Только этот результат предоставляет допуск. Раздел текущего снимка читается после проверки его размера по вычисленному допуску, затем отдельно проверяется по финансовой схеме при `snapshotDate`. Числа из заголовка не увеличивают допуск. Неизвестные поля, лишние/недостающие байты, неподдерживаемые параметры и некорректный UTF-8 отклоняются. Writer возвращает отдельные части, файловый адаптер пишет их последовательно; единый гигантский буфер архива не обязателен.

Даты заголовка проверяются как календарные значения, но сами по себе не ограничиваются текущим днём устройства: часовой пояс или коррекция часов могут различаться. Декодирование использует сохранённые `snapshotDate` и `normalizationDate` для воспроизводимости. Перед пользовательской проверкой и применением уже нормализованный кандидат дополнительно проходит финансовую проверку относительно текущего локального дня; фактические операции из будущего не принимаются. Эта проверка не изменяет исходник или допуск. В парольном варианте даты связаны с разделами аутентификацией; открытый архив криптографической подлинности не обещает.

В восстановленном профиле исходник остаётся неизменяемым основанием допуска. На native он зашифрован вместе с финансовыми данными, а связанный допуск хранится в SecureStore; на Web допуск повторно вычисляется из исходника. Изменяемый снимок не может превысить вычисленные длины. Пока он больше обычного предела, последующие сохранения должны уменьшать его байтовый размер; после достижения предела действует обычное ограничение. Потеря или несогласованность необходимых метаданных не разрешает чтение по произвольному внешнему числу.

### Подготовка, сохранение и проверка копии

Подготовка файла, подтверждение пользователем его сохранения и успешная проверка чтением — разные отметки. Sharesheet не доказывает внешнее сохранение. «Проверить копию» не заменяет финансовое состояние: для отметки последнего экспорта нужны успешное чтение/аутентификация, финансовая валидация и совпадение размера и SHA-256 точных байтов. Другой корректный файл не отмечается как последний экспорт. Повторное шифрование того же учёта даёт другой отпечаток. Для пробного восстановления предусмотрен отдельный новый профиль с явным подтверждением.

Эти отметки хранятся открыто в служебной записи профиля: ID экспорта, имя файла, размер, SHA-256, признак шифрования, вид исходного снимка и даты действий. Финансовый JSON, пароль и ключ в неё не входят. Если текущее сохранение не подтверждено, экспорт последнего читаемого снимка требует отдельного согласия и явно исключает более новые изменения в памяти. Отметки не входят в финансовую копию и не являются криптографическим свидетельством пользователя или внешнего файлового хранилища.

На iOS/Android AES выполняет Expo Crypto, KDF — `@noble/hashes` с уступкой управления циклу событий; web использует WebCrypto (HTTPS или localhost). Пароль не записывается в настройки или копию; поля очищаются после успешного экспорта/чтения. Рабочие массивы ключа и расшифрованного содержимого обнуляются после использования, но JavaScript-строки и копии в памяти ОС гарантированно стереть нельзя. Забытый пароль восстановить невозможно.

При потере ключа или повреждении данных экран ошибки позволяет выбрать JSON или защищённую копию, при необходимости ввести пароль, проверить данные и отдельно подтвердить замену хранилища. Восстановление создаёт ключ с новым ID; прежний ключ не заменяется до записи нового конверта, поэтому прерванная до записи операция не лишает доступа к старому конверту. При удалении приложения ключ может быть утрачен; на iOS элементы Keychain могут пережить переустановку. Перенос платформенной резервной копии на другое устройство не заменяет экспорт отдельной резервной копии.

Веб-предпросмотр использует незашифрованное локальное хранилище браузера. Системная блокировка и нативные напоминания в нём недоступны; интерфейс сообщает об этом.

## Проверка

Автотесты ядра хранилища используют реальный AES-GCM Node.js и тестовые адаптеры хранения. Они покрывают миграцию, Unicode, свежий IV, ошибки записи, повреждённый тег, отсутствие ключа и восстановление. Отдельные тесты исполняют нативный адаптер и проверяют преобразование base64 в байты перед `AESSealedData.fromCombined`: Android в SDK 57 требует массив байтов, хотя публичные типы Expo также разрешают строку. Это не тесты системного Keychain/Keystore или биометрии. Для переносимой копии дополнительно проверяются совместимость WebCrypto и Node.js AES-GCM, совпадение нативного KDF с WebCrypto, неверный пароль, подмена соли/nonce/тега и ограничения недоверенного файла. Скорость KDF, AES и обмен защищённым файлом на реальных телефонах ещё нужно проверить. Проверка на реальных iOS/Android устройствах обязательна перед выпуском; [текущий отчёт](VERIFICATION.md).

Для нового rescue-формата модульные проверки дополнительно покрывают изменённый снимок, выросший за обычный предел, обе формы защиты, чтение текущего раздела только после допуска, связанные с заголовком теги, перестановку разделов и неизменность контракта версии 1. Проверки файловых адаптеров исполняют настоящий TypeScript с тестовыми платформенными модулями; они не заменяют системный picker и Sharesheet. Android-прогоны [T01/A04](tasks/2026-10-06-follow-up/reports/A04-native-security.md) выполнены до изменений T02 и не подтверждают новый формат на телефоне.

Источники текущих API: [Expo Crypto SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/crypto/), [SecureStore SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/securestore/), [LocalAuthentication SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/local-authentication/), [ScreenCapture SDK 58](https://docs.expo.dev/versions/v58.0.0/sdk/screen-capture/). Совместимость используемых вызовов проверена TypeScript с установленными пакетами SDK 58; исторические проверки SDK 57 выше не являются нативной приёмкой SDK 58.

Описание форматов и порядка действий: [перенос данных](DATA_PORTABILITY.md). KDF: [официальная документация noble-hashes](https://github.com/paulmillr/noble-hashes#pbkdf2).

Запрос курсов к Frankfurter содержит только коды валют; учёт, имена и суммы не передаются. Данные курсов и ручные корректировки входят в финансовое хранилище и полные копии. Автообновление можно выключить в настройках валют.

## Черновики форм

Операция и первоначальная настройка имеют отдельные слоты в `lad-profile-<id>:lad-drafts-v1`, вне финансового JSON и переносимой копии. Автосохранение использует задержку 500 мс; после запуска поля предлагаются для восстановления, без автоматического применения. Ограничения: 64 KiB UTF-8 на слот, ограниченные строки/массивы/глубина; пароли, секретные ключи и вложения не принимаются.

[Нативный адаптер](../src/infrastructure/storage/draftStorage.native.ts) шифрует небольшой документ AES-256-GCM отдельным случайным ключом профиля в SecureStore (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`). Каждый шифротекст получает новый nonce; AAD связывает назначение, профиль и ID ключа. Утраченный или недоступный ключ существующего документа не заменяется новым и не вызывает сохранение открытых полей. Web использует открытый JSON в браузерном хранилище.

[Протокол](../src/infrastructure/storage/draftStore.ts) проверяет запись чтением и использует владельца, поколение и отметку удаления: запоздалая очередь не может вернуть удалённый черновик или затереть другую запись. Перед заменой учёта сохраняется блокирующая отметка с отпечатками исходного и ожидаемого снимка. После перезапуска точный снимок определяет очистку либо возврат старого черновика; неизвестный результат оставляет поля заблокированными. Ошибку чтения можно повторить или явно удалить все черновики профиля.

В Т04 протокол и браузерные сценарии проверяются в Chromium; AES-проверки с WebCrypto не подтверждают работу SecureStore или Expo Crypto на телефоне. Аварийное завершение, блокировка и стоимость автосохранения iOS/Android остаются отложенными по указанию пользователя. Повторное чтение не является гарантией сохранности при отключении питания.
