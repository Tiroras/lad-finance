# Агенты для мобильных проверок

В проекте определены три агента Codex для Maestro. Они выполняют последовательность «план → сценарий → разбор падения», аналогичную [Playwright Test Agents](https://playwright.dev/docs/test-agents). Это проектные роли с инструкциями; действия на устройстве предоставляет уже подключённый [Maestro MCP](https://docs.maestro.dev/get-started/maestro-mcp).

| Агент               | Задача                                               | Результат                                                                          |
| ------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `maestro_planner`   | Исследовать интерфейс и выбрать случаи для проверки  | План в `tests/mobile/plans/<feature>.md`                                           |
| `maestro_generator` | Выполнить шаги плана и записать проверяемый сценарий | YAML в `tests/mobile/<mode>/<scenario>.yaml` и результат запуска                   |
| `maestro_healer`    | Воспроизвести сбой и определить его причину          | Исправление теста с повторной проверкой либо описание дефекта приложения/окружения |

Определения находятся в [.codex/agents/](../.codex/agents/). Они используют настройки модели, разрешений и MCP родительского сеанса. Глобальная конфигурация не меняется. Формат соответствует [проектным агентам Codex](https://learn.chatgpt.com/docs/agent-configuration/subagents).

## Как использовать

Откройте репозиторий в актуальном Codex CLI или расширении и начните новый сеанс после добавления файлов. Maestro MCP должен быть подключён, а выбранный тестовый эмулятор — доступен. Подготовка описана в [Docker-инструкции](DOCKER.md) и [README](../README.md#maestro-mcp-для-codex).

Примеры поручений:

> Используй maestro_planner: составь план проверки операций Лада в режиме Demo на доступном тестовом Android-эмуляторе. Исследуй интерфейс, запиши исходные данные и ожидаемые результаты.

> Передай maestro_generator план tests/mobile/plans/transactions.md. Создай и выполни сценарии на том же устройстве в режиме Demo.

> Используй maestro_healer для падения tests/mobile/demo/transactions.yaml. Воспроизведи ошибку, сохрани смысл проверок и сообщи, если проблема в приложении.

Для полного цикла можно одним поручением попросить последовательно использовать planner и generator, а при падении — healer. На одном эмуляторе в каждый момент работает только одна роль. Названия агентов указываются обычным текстом; это не команды `npm` и не навыки с префиксом `$`.

Если клиент не загрузил проектные роли, начните новый сеанс или обновите Codex. До этого основной агент может прочитать нужный TOML и выполнить его процедуру сам; такой запуск следует описывать как выполнение роли основным агентом.

## Общие правила работы ролей

- Передавайте между этапами задачу или путь к плану, `deviceId` и имя AVD, режим, выбранное подключение MCP, способ запуска (Docker или локально), сведения о подготовленной сборке и разрешённых тестовых данных. Согласованные условия сохраняются на следующих этапах.
- Получите устройства через доступный MCP и явно выберите нужное. Не управляйте одним устройством одновременно через другой агент, CLI-тест и MCP. Сначала дождитесь завершения предыдущего этапа.
- Используйте инструменты, которые объявляет подключённый сервер. В Maestro 2.11 доступны `list_devices`, `inspect_screen`, `take_screenshot`, `run`, `cheat_sheet`; названия и аргументы уточняйте по фактической схеме. В контейнерном MCP путь к репозиторию — `/workspace`, в локальном — путь клона на компьютере.
- Выбирайте режим до исследования и запуска. Данные для изменений должны быть тестовыми. Fresh и `clearState` удаляют учёт; используйте их только на выделенном тестовом устройстве в рамках согласованной подготовки. Пересборка с `adb install -r` сама по себе профиль не очищает.
- `--no-build` разрешён, когда установленная release-сборка уже соответствует нужным исходникам и режиму. После изменений продукта или смены режима выполняйте полную сборку. Не приписывайте YAML-переменным `EXPO_PUBLIC_*` способность менять уже собранный APK.
- Артефакты запуска и снимки сохраняйте в игнорируемом `test-results/mobile/`. План и YAML остаются в репозитории. Отделяйте фактически пройденные сценарии от черновиков, недоступных проверок и найденных дефектов.

## Три режима

| Режим     | Когда использовать                        | Особенность                                                               |
| --------- | ----------------------------------------- | ------------------------------------------------------------------------- |
| `default` | Личный учёт, сохранение после перезапуска | Существующие данные загружаются; пустой профиль нужно подготовить явно    |
| `demo`    | Заполненные экраны и готовые примеры      | Включение опции добавляет профиль «Демо»; сценарий должен сам его выбрать |
| `fresh`   | Приветствие, обучение, пустые состояния   | Debug и Metro; каждый новый запуск JS очищает все профили                 |

Fresh нельзя использовать для сценария «создать операцию → перезапустить приложение → убедиться, что операция сохранилась». Такой сценарий проверяется в `default` или `demo` с выключенной очисткой.

Полный запуск через Docker сам готовит нужную сборку. Например, после создания файла сценария:

```sh
docker compose run --rm android test --mode demo --device emulator-5554 tests/mobile/demo/transactions.yaml
```

Подставьте идентификатор выбранного тестового устройства. Для интерактивного исследования Fresh через MCP нужен уже работающий Metro с `EXPO_PUBLIC_RESET_ON_START=true` на порту debug-сборки и соответствующий ADB reverse. Команда `android test --mode fresh` с явно указанным сценарием управляет своим Metro только на время CLI-теста и останавливает его после завершения; не считайте её постоянным сервером для MCP. Если такого сервера нет, выполните готовый Fresh-сценарий полным запуском через Docker, а непроведённое интерактивное исследование отметьте отдельно.

## Размещение сценариев

Общего smoke-сценария нет. Новые сценарии размещайте в `tests/mobile/default/`, `tests/mobile/demo/` или `tests/mobile/fresh/` по требуемому режиму, общие подшаги — в `tests/mobile/subflows/`. Создавайте каталоги по мере появления файлов.

Команды `npm run test:mobile -- …` и `docker compose run --rm android test …` требуют явного пути к файлу или папке сценариев. Без пути они завершаются с подсказкой до подготовки устройства и сборки. Для папки Maestro запускает только YAML верхнего уровня, поэтому `tests/mobile/` не находит сценарии из подпапок режимов. Не включайте рекурсивный запуск всех режимов одним glob: один установленный APK не может одновременно работать во всех трёх режимах. [Правила поиска сценариев Maestro](https://docs.maestro.dev/maestro-flows/workspace-management/test-discovery-and-tags).

Существующий [demo/refactoring.yaml](../tests/mobile/demo/refactoring.yaml) проверяет операции и форматируемые поля. Ему нужны Demo, завершённое приветствие, локальная дата устройства `2026-10-04` и исходные демоданные из [плана проверки](../tests/mobile/plans/refactoring.md#реализованный-сценарий-и-подготовленная-сборка). Перед запуском выполните подготовку из плана; при другой дате сначала согласованно обновите даты и ожидания. Полный запуск после подготовки:

```sh
docker compose run --rm android test --mode demo tests/mobile/demo/refactoring.yaml
```

В комментариях сценария укажите требуемый режим и относительный путь к плану. В самом плане зафиксируйте подготовку данных и ожидаемые результаты, включая суммы, валюты и условия повторного запуска. Успешная навигация сама по себе не подтверждает корректность финансового расчёта.
