## Выбранный минимальный объём

[BackupSettings](../../../../src/features/data-transfer/components/BackupSettings.tsx) и [backup.ts](../../../../src/features/data-transfer/lib/backup.ts) уже создают полный JSON одного профиля и `.ladbackup`. [DataManagement](../../../../src/features/data-transfer/components/DataManagement.tsx) подтверждает замену профиля; [CSV-импорт](../../../../src/domain/csv.ts) добавляет проверенные операции. Эти механизмы сохраняются.

Базовый объём реализации: полный JSON/защищённая копия; выбор счёта/периода CSV; автоматические CSV-части; экраны результата. A03 следует [контракту T02](recovery-security.md): архив точного проверенного исходного JSON, без повторной сериализации выросшего после нормализации кандидата. При незаписанных изменениях источник явно обозначается последним читаемым сохранённым снимком, а не текущим UI. Восстановление большого архива — в новый профиль. CSV этот маршрут не заменяет.

Выборочный JSON, объединение двух полных финансовых состояний и атомарный импорт всех CSV-файлов набора **не рекомендуются в первый этап**. Они увеличивают область финансовых правил без необходимости для выбранного минимального пути. Это результат анализа, а не незавершённый поиск вариантов.

## A07: как формировать CSV-части

[exportTransactionsCsv](../../../../src/domain/csvExport.ts) уже сортирует операции по дате/ID, применяет фильтры и формирует строки частей покупки/возврата. В универсальном CSV перевод остаётся одной записью с двумя суммами и валютами. Его нельзя преобразовывать в два независимых расхода/дохода.

Алгоритм разбиения использует готовые логические CSV-записи после экранирования. Предел каждой части — 5000 строк данных и 2 000 000 UTF-8 байт **включая заголовок**, BOM при наличии и разделители. Перенос строки внутри кавычек не является границей записи. Сохранять строки одной операции в одной части; исходный `GroupID`/`RefundOf` не перенумеровывать. Покупка и её возврат могут оказаться в разных частях: ссылка сохраняется в тексте, но автоматическое восстановление связи не обещается.

Использовать детерминированный порядок и имена вида `lad-<дата>-<набор>-001-of-004.csv`. ID набора создаётся один раз при подготовке, все части относятся к одному неизменяемому снимку и одинаковым фильтрам. Сводка содержит число операций, строк, файлов, байт и период. Если неделимая группа превышает предел, экспорт прекращается с объяснением; обрезки и молчаливого пропуска нет. Для такого случая предлагается полная копия, а не фиктивно пригодный CSV.

Минимальный интерфейс предоставляет список частей и отдельную передачу каждого файла через существующий [shareFile](../../../../src/infrastructure/files/shareFile.native.ts). ZIP и многократные системные диалоги без участия пользователя не нужны. Статус подтверждения хранится отдельно для каждой части; весь набор подтверждён только после всех частей. Повтор передачи использует тот же подготовленный файл/снимок, а изменение фильтров создаёт новый набор.

Обратный CSV-импорт остаётся последовательным и атомарным **для одного файла**. Если третья часть не принята, первые две сохраняются; сводка объясняет результат и позволяет исправить следующую. Сам факт разбиения не делает формат без потерь: начальные остатки, планы, цели, долги и связи разделений сохраняет полная копия.

## A06: состояния импорта и записи

Контракт: `выбор → чтение/проверка → предпросмотр → подтверждение → применение → сохранение → результат`. Отмена до применения не меняет учёт. CSV подтверждает выбранный пакет; JSON отдельно подтверждает замену названного профиля. Пароль, повреждённый файл и недопустимый кандидат завершают проверку ошибкой до изменения состояния.

Применение повторно проверяет актуальный профиль и весь кандидат через доменное действие внутри обновления. Счётчики результата вычисляются там же; разность со старым UI-предпросмотром не является доказательством. На время применения/сохранения блокируются повторное подтверждение, смена профиля и конкурирующие финансовые действия.

Экран «Сохранено» появляется после проверяемого сохранения через [FinanceProvider](../../../../src/state/finance/FinanceProvider.tsx). Одного [queue.flush](../../../../src/state/finance/saveQueue.ts) недостаточно: ошибки записи подавляются очередью, а `flushCurrentProfile` проверяет соответствие `lastSaved` ожидаемому снимку. Этот контракт должен связывать подтверждение с конкретной операцией и профилем.

При отказе записи состояние уже могло измениться в памяти. Показывать «Изменения применены, запись не подтверждена» и кнопку повтора **сохранения**, не повторного импорта. Не обещать автоматический откат: запись могла завершиться перед ошибкой обратной проверки. Повторное открытие результата не вызывает действие снова; после перезапуска файл автоматически не импортируется.

Сводка показывает профиль, формат, режим, добавленные/пропущенные/заменённые записи, причины пропуска, число счетов и остатки по валютам. Число источниковых строк отличать от числа операций. Пароли, содержимое заметок и ключи в историю результата не сохранять.

## A06: состояния экспорта и внешнего сохранения

Контракт: `подготовка → файл готов → передача системе → результат неизвестен → подтверждено пользователем / не подтверждено`. Ошибка подготовки/передачи — отдельная ветка. Профиль, снимок и параметры фиксируются до асинхронной подготовки; последующая смена профиля не переименовывает результат.

[Sharing.shareAsync](https://docs.expo.dev/versions/v57.0.0/sdk/sharing/#sharingshareasyncurl-options) открывает системное меню и возвращает `Promise<void>`, без подтверждённого пути сохранённой копии. Поэтому успешное разрешение promise не превращается в «сохранено». Если адаптер достоверно сообщает отмену, показать её; иначе после возврата спросить в интерфейсе «Вы сохранили файл?» с действиями «Да», «Ещё нет» и «Проверить файл». Нельзя выводить отмену из одного только отсутствия ошибки.

«Да» означает **подтверждено пользователем**, с отдельной датой. «Проверить файл» сравнивает внешний файл с результатом и проверяет копию без восстановления. «Ещё нет» позволяет повторить передачу. Браузерное скачивание также не доказывает запись на диск. [История подготовки](../../../../src/infrastructure/storage/backupHistory.ts) сохраняет прежний смысл. Отмена/ошибка не создаёт положительного подтверждения.

Повтор передачи использует те же байты. После удаления нативного cache-файла его можно восстановить из оставшегося буфера; если буфер утрачен, новая генерация означает новый экспорт. У `.ladbackup` свежие соль/nonce меняют файловый хеш даже при прежних финансах. Сравнение содержимого возможно после расшифрования: отпечаток включает версию алгоритма канонизации, финансовой схемы и фиксированную дату нормализации. Будущая миграция не переиспользует старый отпечаток молча; несовместимые версии подтверждают только читаемость, не равенство прежнему снимку.

## A26: рекомендованные режимы и предел добавления

| Режим                                         | Решение                                                                                           |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Полная копия → текущий профиль                | Сохранить replace с предпросмотром, предложением копии прежнего состояния и явным подтверждением. |
| Полная копия → новый профиль                  | Реализовать как безопасный альтернативный маршрут T02, особенно для большого архива.              |
| CSV → текущий профиль                         | Сохранить add выбранных новых операций и текущую проверку повторов.                               |
| Полный/выборочный JSON → существующий профиль | Отложить merge; автоматического сложения состояний не делать.                                     |

[restoreFinance](../../../../src/domain/actions/settings.ts) проверяет полный кандидат. Замена не складывает начальные остатки и не присваивает новые ID каждой записи: повтор той же копии снова задаёт тот же снимок. Профиль назначения и его идентичность сохраняются. Архивные категории и исторические связи полной копии остаются частью проверяемого состояния.

Для будущего add одинаковый ID с разным содержимым является конфликтом; совпадающее название счёта не доказывает тождество. Нужны явное сопоставление счетов/валют, правило начальных остатков и корректировок, решение по основной валюте и историческим `baseAmount`. Переназначение ID обязано обновлять **все** ссылки: части, возвраты, долги, цели, исполнения планов, сценарии и идентификаторы импорта. Архивные категории нельзя автоматически оживлять или удалять; добавление новых операций проверяет действующие ограничения. Неопределённый конфликт блокирует пакет, а не выбирает победителя молча.

Будущий merge должен сначала построить полный неизменяемый кандидат, проверить финансовые инварианты, дедупликацию и лимиты, затем выполнить одно применение. Повтор того же источника должен иметь определённую идемпотентность. Эти условия объясняют отказ от merge на первом этапе, но не авторизуют его реализацию.
