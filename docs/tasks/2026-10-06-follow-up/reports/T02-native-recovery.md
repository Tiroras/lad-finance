# T02: восстановление и проверка копий на Android

Дата: 2026-10-15. Статус нативной приёмки: **частично выполнена; оставшиеся проверки отложены по указанию пользователя**. B10 и малое пробное восстановление прошли. После исправления `SQLITE_FULL` на новой APK прошли продолжение того же pending import, restart, полный actual plain/password oracle и повторные полные экспорты исходного/контрольного профилей. Независимый перенос на чистый 5562 начат, но результат не подтверждён. Режим `default`, Fresh/clearState не применялись. Физические Android и iOS — **not-run**. Нативные проверки в этой сессии больше не выполняются; разрешены только браузерные проверки.

## Стенд и инцидент с каталогом артефактов

Во время подготовки параллельный Playwright-запуск очистил общий `test-results/`. Были утрачены прежние host-логи и файлы AVD, в том числе данные работающего `Lad_FirstRun_Test` (`emulator-5556`). Это ошибка организации тестового окружения, не действие Лада. Живой процесс QEMU продолжил держать открытые, уже удалённые файлы диска; приложение оставалось доступно. Утраченные артефакты не считаются доступными доказательствами нового прогона.

До остановки старого эмулятора через ADB сохранён установленный T01 APK: SHA-256 `29047a83a245f4676b83b0247bdc608521a9cc3268b0acee95d1d649194f8a45`, совпадает с историческим отчётом. Затем через обычный UI/Android Sharesheet/реальный `A04 Test Receiver` заново экспортирован исходный `A04-20261015-Android`: 2 191 байт, SHA-256 `4eb02ccaf79413515d63de172ebc56a0ec4704c05c60af30ef69b7e53a09ba5c`. Новый полный JSON oracle подтвердил все финансовые поля эталона (3 операции, 3 счёта, 1 цель); это отдельное текущее сохранение, а не воссоздание удалённых логов T01.

Все новые native-артефакты размещаются в `test-artifacts/t02-native/`, вне outputDir Playwright. Список прежних синтетических профилей: `Личный`, `A04-20261006`, `A04-20261015-Android`, `A05-20261015-Control`, `A05-20261015-Offline-Control`. Все пять сохранены во внешние файлы до завершения старого процесса; полный перечень размеров, SHA и проверок — `test-artifacts/t02-native/preserved/profiles-manifest.json` и `profiles-oracle.log`. Новый AVD `Lad_T02_Recovery_Test` / `emulator-5560` использует отдельные userdata и ключи в `test-artifacts/t02-native/avd-replacement`; исходные диски и Keystore не клонируются. Новый AVD загрузился за 122 887 мс; первоначальный ADB offline исправлен адресным reconnect только `emulator-5560`. Сохранённые APK установлены; SHA установленной T01 APK повторно проверен на устройстве. Все пять профилей выгружены и прошли финансовую валидацию/roundtrip. Контрольный A05 восстановлен в новом «Личный»; его настоящий повторный экспорт полностью равен исходному JSON (2 404 байта, SHA-256 `07fa687e130896bd21119e656885627facc6ef31ea3d8464a064952c79e79d91`). При разрешённой попытке остановить старый 5556 его консоль уже была недоступна, PID 81015 отсутствовал; точная причина прежнего завершения не установлена. К этому моменту все JSON и APK уже были сохранены. Исходный A04 восстановлен в отдельный одноимённый профиль; его повторный фактический экспорт снова прошёл полный oracle (2 191 байт, SHA `4eb02ccaf79413515d63de172ebc56a0ec4704c05c60af30ef69b7e53a09ba5c`). Остальные три профиля сохранены во внешних проверенных файлах, но на новом стенде не создавались. Это новая установка с новым ключом, а не продолжение прежнего Keystore.

## Сборка

Первая промежуточная сборка `docker compose run --rm android build --abi arm64-v8a` завершилась успешно. APK SHA-256 `76cd8e9aade12b12d55b281647b0e3eb05a6d248adf39532953da419e296307b`. Во время сборки независимое ревью исправило три storage-файла; pre/post manifests различаются. Эта APK **не установлена и не используется как окончательная версия T02**. Повторная окончательная сборка после заморозки прошла: APK SHA-256 `4a9b484149b0620b8f5c999f6952ad8b297f5e86b140a3c1806badf20b035e0f`, pre/post manifest 344 файлов одинаков: `907109c6c44b0aab3d9fd76cea8ddb204c79ac6eeb3ae867e98d048c34161f9f`. После восстановления исходного и контрольного профилей APK установлена через `adb install -r`; хеш установленного файла совпал. Независимая повторная проверка root подтвердила совпадение всех 344 входных файлов во время нативного прогона. Fresh/clearState не применялись.

Стенд: Android 17 / API 37, arm64-v8a, Hypervisor.Framework, 2 vCPU, 4 GiB RAM, 720×1600 / 280 dpi; фактический графический backend — SwiftShader. Во время этих проверок окно эмулятора было открыто. Часовой пояс устройства — `Europe/Samara`; проверено `2026-10-15T17:26:20+0400`, локальная дата совпадает с host. Wi-Fi и mobile data временно выключены для автономных проверок. Эти результаты не измеряют физическое устройство.

После воспроизводимого `SQLITE_FULL` подготовлена отдельная исправленная сборка: `test-artifacts/t02-file-storage/app-default.apk`, SHA-256 `b5683e98e9f6e9307e449fce5a2ded6bc73e4747a577f141981447fcba906068`. Сборка завершилась за 4 мин 12 с; pre/post manifest 346 входных файлов совпал: `7ee99282df6dbcb367650e7842c73966e4fc4d27a5daf9687d7e56cdf06c1933`. Большой шифротекст хранится отдельными неизменяемыми файлами, а AsyncStorage — маленьким указателем; прежние inline-записи остаются читаемыми. APK установлена `install -r`, хеш установленного файла проверен (`file-storage-fix/installed-apk-sha.txt`).

Перед этой установкой в 20:41 ADB уже не видел 5560, процесс QEMU отсутствовал. Контроллер его не останавливал; точная причина выхода не установлена, сохранённый emulator log не содержит доказанной причины. В отличие от прежнего инцидента, userdata в `test-artifacts` сохранились. Тот же диск запущен без wipe и snapshots, boot 19 041 мс (`file-storage-fix/source-cold-start.log`). После установки APK первый assert Maestro подтвердил прежний pending journal; имя `T02-20261015-Large` сохранилось. В `20:43:41 +04:00` повторно записаны timezone `Europe/Samara`, дата 15 октября, выключенные Wi-Fi/mobile (`device-environment.json`).

После `adb push` DocumentsUI не сразу показывал новые файлы; адресный `MEDIA_SCANNER_SCAN_FILE` применён только к трём публичным синтетическим файлам. ## Наблюдения длительности

Это единичные интервалы видимого UI на эмуляторе, не изолированное время PBKDF2, не p95 и не физический benchmark. Итерации PBKDF2-SHA256 остаются 600 000. Для отрицательной попытки: завершение нажатия `2026-10-15 17:27:26.008 +04:00`, явный отказ `17:35:25.643`, интервал **479,635 с**; в середине наблюдалось «Проверка пароля…» (`large-password-busy.png`). Предел ожидания теста 600 с не достигнут. Значение включает работу приложения и задержку наблюдения Maestro.

## Подтверждённый дефект native-хранилища

После исправленного ввода правильный пароль принят: busy исчез в `17:59:43.611 +04:00` (367,014 с от завершения нажатия `17:53:36.597`), явное сообщение «Большая копия проверена…», отсутствие ошибки и запрет замены текущего учёта прошли. Подтверждение состава 9 997 / 3 / 0 и создания `T02-20261015-Large` нажато в `18:00:39.181`.

Запись не завершилась. Приложение показало экран незавершённого восстановления, сохранило pending journal и не открыло пустой профиль. `large-positive-retry.log` завершился ошибкой ожидания активного профиля; restart и полный большой export в той попытке **не выполнены**. До read-only осмотра в 20:22 приложение/AVD не перезапускались, журнал не откатывался, новый KDF не запускался.

Точную причину установил read-only `adb shell dumpsys dbinfo app.lad.finance`: в `18:01:42.511` запрос `INSERT OR REPLACE INTO catalystLocalStorage VALUES (?, ?)` завершился `database or disk is full (code 13 SQLITE_FULL)` за 181 мс. Последующий `ROLLBACK` сообщил `cannot rollback - no transaction is active`. На устройстве `/data` имел 8,8 GiB свободного места; после неуспешной транзакции `RKStorage` занимает 40 960 байт. Это отказ базы native storage, не ошибка переносимого пароля. Точный SQLite текст отсутствовал в сохранённом logcat и получен из истории операций открытого SQLite connection pool, без чтения финансовых записей.

Артефакты: `large-create-dbinfo-20261015-2024.txt`, `large-create-device-disk-20261015-2025.txt`, первоначальный `large-create-observation.png`, повторный `large-create-current-20261015-2022.png`, полный debug `large-positive-retry-debug/`; размеры и SHA перечислены в `large-create-failure-manifest.json`. Повторный read-only осмотр после паузы в 20:22 подтвердил тот же PID 20645 и тот же экран. Защищённый actual export и перенос на независимый 5562 до исправления не выполнялись.

Продолжение **pass**: `t02-resume-pending-large.yaml` возобновил существующий pending-import через точный открытый v2 после исправления и новой APK. Host `resume-candidate-equivalence.json` подтвердил полное равенство identity/source/current/state для plain и ранее расшифрованного password-файла; защиты `none` и `password` проверены явно. Pending journal и неизменённое имя проверены после обновления; подтверждение того же состава 9 997 / 3 / 0 нажато в `20:47:57.612 +04:00`. Профиль открылся в `20:54:20.069` (382,457 с), незавершённое восстановление больше не видно. После stop/launch (`20:54:21.998`) сохранённый профиль снова открыт в `20:59:38.251` (316,253 с), все три остатка прошли. Это наблюдаемые UI-интервалы всей операции, не длительности изолированного шифрования.

Actual plain export: нажатие `20:59:54.329` → Sharesheet `21:04:05.470` (251,141 с), новый receiver callback `21:04:06.360` (`1792083846360`), `SUCCESS` виден в `21:04:08.778`; CLI exit 0. Файл `file-storage-fix/source-plain/received-1792083846463-b4156468.ladbackup` содержит открытый rescue v2: расширение локального приёмника не определяет защиту, header явно проверен как `none`. Размер 10 138 489 байт, SHA-256 `351eb266877a8b3b44c063fe5b48a278f71f10aeb74ea4a9cb62021fbf160d49`. `source-plain-oracle.log` подтвердил точный immutable source, полный текущий JSON и state SHA `4eb80d95737ebb9ba49d63bf10fa2e2fa8acd63eb10f58df89e7ec7cd551c9df`, включая удалённые прежние операции и новую `a03-later`. Это также успешное продолжение A01 после реального сбоя записи, но не проверка потери ключа/повреждения каталога.

Protected actual export **pass**, clean-target roundtrip **отложен по указанию пользователя без подтверждённого результата**; прежний decrypt не заменяет проверку нового экспорта.

Во время ввода нового пароля были отдельные задержки harness: первый `inputText` — 127,921 с, фокус повторного поля — около 223 с; второй `inputText` — 7,555 с.
