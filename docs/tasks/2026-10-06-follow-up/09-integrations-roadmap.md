## Анализ

В B11 перечислены восемь самостоятельных направлений, а не одна функция: банки, синхронизация, совместный учёт, реальные платежи, OCR/QR чеков, инвестиционный портфель, удалённые push и нативные виджеты. Пользователь запросил аналитику, включая риск платного банковского API, и уточнил рынок: популярные российские банки. Итог находится в [аналитической записке](analysis/integrations.md).

Для первого охвата выбраны Сбер, Т-Банк, ВТБ и Альфа-Банк; это практическая выборка, не статистический рейтинг. Бюджет и масштаб не заданы. Стандарт Open API, публичная документация банка, API бизнес-счёта и разрешённый доступ к личным счетам пользователя — разные основания. Нельзя считать все API платными или обещать бесплатную агрегацию всех банков.

## Принятые аналитические решения

1. Начинать с проверенных файловых импортов и восстановления локальных копий (T02/T03). Следующая необязательная ступень — перенос зашифрованной копии в выбранное пользователем облачное хранилище; это ещё не синхронизация и не семейный учёт.
2. Сбер и Т-Банк публикуют бесплатные бизнес-API; рассмотренный ВТБ API также относится к бизнесу, отдельная цена не установлена. Эти сведения не подтверждают доступ к личным картам. Все ссылки и пределы проверки приведены в записке.
3. Альфа — первый кандидат для дальнейшей проверки допуска: опубликованы счета ФЛ и методы истории операций, scope `operations-history`; общая инструкция Alfa API заявляет отсутствие комиссии за подключение/использование. Нужны РКО, Альфа-Бизнес, договор и подготовка интеграции. Допуск «Лада» к конкретному scope, квоты, актуальная доступность методов и применимые условия не подтверждены. Часть страниц проверена по индексированному официальному тексту из-за timeout/502 при прямом открытии.
4. Архитектура сохраняет чистый domain, изменения через domain actions и `update(current => …)`, единый финансовый state и платформенные адаптеры. Общие партнёрские секреты не встраиваются в приложение; собственный сервер появляется только после выбора сценария, требований и бюджета.
5. Виджеты и локальное распознавание оцениваются независимо от банков; для Expo SDK 57 путь `expo-widgets` относится к iOS, Android требует отдельного App Widget. Семья зависит от полноценной синхронизации и прав; удалённые push — от серверных событий; реальные платежи — от отдельного допуска и сверки исполнения.
6. Сценарии стоимости: A — автономный учёт без расходов на банковский API/свой сервер; B — A плюс выбранное хранилище копий; C — промышленное банковское подключение с РКО/партнёрскими условиями, инфраструктурой и сопровождением. Формула оставляет неизвестные цены открытыми. Рекомендован A, при необходимости B; C — один банк после подтверждения доступа и бюджета.

Для промышленного банковского подключения сейчас NO-GO из-за неподтверждённого допуска/условий, а не доказанной дороговизны. Это не препятствует завершению аналитики и дальнейшему локальному проектированию.

## Порядок работы

1. Для всех восьми направлений описать полезный минимальный вариант, данные, архитектурные зависимости, затраты и способ проверки.
2. Сначала рассмотреть функции без банковского API: файлы выписок через системный выбор/обмен, ручной портфель, локальное распознавание с подтверждением, виджеты с минимальным набором данных. OCR не превращает изображение в подтверждённую операцию автоматически; QR не гарантирует доступ к содержимому чека.
3. Отдельно спроектировать синхронизацию и совместный доступ: версии записей, конфликты, удаления, права, ключи, автономная работа и выход участника. Синхронизация файла копии ещё не означает безопасный совместный учёт.
4. Для банков составить таблицу кандидатов: география/тип клиента, личные счета, история и остатки, доступ к тестовой и рабочей среде, согласие и отзыв, договор, лимиты, тариф и статус подтверждения сведений. Неизвестные цены оставить неизвестными и указать, как получить коммерческое предложение; никому не писать без отдельного поручения.
5. Разделить чтение выписки и инициирование платежа. Второе требует отдельного провайдера, подтверждения пользователя и защиты от повторной отправки; в эту задачу входят только проектирование и критерии допуска.
6. Выстроить этапы внедрения, возможность работать без подключения и оценку расходов: подключение, активные пользователи/счета, запросы, хранение, push, поддержка и сопровождение. Для SDK/сервиса без публичного тарифа не выдумывать стоимость.

## Приёмка

План охватывает все восемь направлений, содержит проверенные официальные источники с датой, различает доступность API и цену, предусматривает полезную версию без платного банковского доступа. Для каждого этапа есть условие начала, критерий готовности и способ отключения интеграции без потери локального учёта. Партнёрские доступы и платные услуги не приобретаются в рамках подготовки документа.

Аналитическая задача не требует запуска приложения. После выбора конкретного внешнего сервиса условия и тариф нужно проверить заново. Задача закрывается итоговым документом, а не реализацией всех перечисленных функций.
