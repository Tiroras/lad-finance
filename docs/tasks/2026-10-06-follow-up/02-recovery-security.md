## Анализ

Повреждение [реестра профилей](../../../src/infrastructure/storage/profileStorage.ts) блокирует обычное восстановление, хотя отдельные финансовые записи могут оставаться исправными. Нельзя обходить эту защиту автоматическим созданием пустого реестра. Большой допустимый старый снимок может читаться, но полный экспорт ограничен новым размером. Нужен выход без удаления истории ради создания первой копии.

Нативное шифрование, открытый JSON и Web дают разные гарантии. Профили не разграничивают доступ людей; усиление привязки ключа к аутентификации может ухудшить восстановимость. Наличие даты подготовленного файла не доказывает наличие пригодной внешней копии. Основания: [SECURITY](../../SECURITY.md), [DATA_PORTABILITY](../../DATA_PORTABILITY.md), [варианты экспорта](analysis/import-export.md).

## Принятые аналитические решения

1. **A01:** основной маршрут — сканирование допустимых пространств профилей без записи, затем подтверждённое восстановление каталога. Обычный `load()` не используется для обнаружения, поскольку может мигрировать и удалить plaintext. Для потерянных названий предлагаются уникальные временные имена. Недоступные записи сохраняются.
2. **Фиксация A01:** служебный журнал хранит исходный и кандидатный каталог, ID операции и стадию без финансового содержимого. Основной каталог заменяется после проверки кандидата; предпочтение активного профиля записывается затем. Прерывание возобновляет ту же операцию. Это логическая согласованность, не обещание транзакции между AsyncStorage и SecureStore.
3. **A03:** выбран однофайловый архив точных исходных байтов JSON версии 1–4: пределы 5 000 000 UTF-16 единиц и 15 000 000 UTF-8 байт относятся к источнику. После нормализации кандидат может вырасти; повторный входной лимит к нему не применяется. Выбран двухпроходный writer: точные длины проверенного кандидата рассчитываются до выделения полного буфера, затем контролируются при записи. Допуск связан с исходником/версией нормализации, проверяется после перезапуска и разрешает только уменьшение; reader валидирует объект отдельно от входного лимита. Глобальные 5 МБ не повышаются. Защищённый архив использует конверт версии 2 с отдельным AAD; версия 1 сохраняет контракт. Восстановление только в новый профиль, затем уменьшение. При неподтверждённой записи экспорт обозначается последним читаемым сохранённым снимком, не текущим UI. T01 проверяет ресурсы; CSV не заменяет архив.
4. **B09:** сохранить существующий ключ на профиль без автоматического `requireAuthentication`, открытый минимальный каталог и точные пояснения границ. Усиление ключа/шифрование имён отложить как отдельную опцию с миграцией и восстановлением; не ослаблять ключ ради фоновых задач.
5. **B10:** основной маршрут — «создать → сохранить вне приложения → выбрать файл и проверить без замены». Он не меняет учёт, реестр и ключи. Дополнительное пробное восстановление возможно только в отдельный профиль после подтверждения. Подготовка, подтверждение пользователем и проверка чтения — разные статусы.

## Работа и приёмка

- Реализовать изолированное восстановление реестра с подтверждением и журналом стадий. Повтор после сбоя идемпотентен; чужие профили, исходные ключи и снимки сохраняются. Проверить отсутствие побочных записей при сканировании.
- Создать полную копию валидного старого снимка больше 5 МБ и доказать обратное чтение с сохранением всех сущностей, сумм и ссылок. Повреждённые/слишком большие неподдерживаемые входы безопасно отклоняются. Лимиты нельзя просто снять глобально.
- Показать состав копии: текущий профиль, включённые финансовые данные и исключённые метаданные. Проверка чтения не вызывает восстановление; проверка другого файла не подтверждает последний экспорт.
- Проверить повреждённый реестр при исправном/повреждённом учёте, отсутствие ключа, сбой записи нового профиля, повтор восстановления, неверный пароль, отмену, большой архив и перенос между тестовыми устройствами.
