# Архитектура и границы модулей

Этот документ дополняет [AGENTS.md](../AGENTS.md) и задаёт обязательные правила изменения кода приложения. Перед созданием или переносом файла определите его ответственность по таблице и расширяйте соответствующий модуль.

## Размещение файлов

Не возвращайте общие каталоги `src/forms/`, `src/hooks/`, `src/services/`, `src/ui/`, `src/security/`, `src/navigation/` и отдельные `src/Application.tsx`, `src/store.tsx`, `src/backup.ts`.

| Расположение                                                                     | Назначение                                                                                      |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `App.tsx`, `src/application/Application.tsx`                                     | Точки входа, загрузка шрифтов, композиция приложения                                            |
| `src/application/providers/`                                                     | Сборка существующих провайдеров в `AppProviders.tsx`                                            |
| `src/application/navigation/`                                                    | Контракты вкладок и окон, переходы, Android Back, переходы из уведомлений, навигационные панели |
| `src/application/shell/`                                                         | Оболочка, шапка, окна, загрузка и уведомления интерфейса                                        |
| `src/screens/{home,transactions,plan,analytics}/`                                | Композиция экранов и разметка, нужная только конкретному экрану                                 |
| `src/features/<feature>/components/`                                             | Формы, карточки и другие компоненты предметной функции                                          |
| `src/features/<feature>/model/`, `lib/`                                          | Собственные провайдеры, хуки, черновики и вспомогательная логика функции                        |
| `src/features/<feature>/index.ts`                                                | Узкий публичный интерфейс модуля                                                                |
| `src/domain/`, `src/domain/actions/`                                             | Финансовая модель, чистые расчёты, CSV, проверка копий; валидируемые изменения состояния        |
| `src/state/finance/`                                                             | `FinanceProvider`, очередь сохранений, смена дня, `useFinanceActions`, `useMoney`               |
| `src/infrastructure/{storage,crypto,device,files,notifications,exchange-rates}/` | Платформенные адаптеры хранилища, шифрования, защиты, документов, уведомлений и сетевых курсов  |
| `src/shared/ui/`                                                                 | Универсальные компоненты, тема, типографика и состояния взаимодействия                          |
| `src/shared/lib/`                                                                | Универсальные функции и хуки, календарные даты, `useActionError`                                |
| `tests/`, `tests/e2e/`, `tests/mobile/`                                          | Модульные проверки, сценарии Playwright и Maestro                                               |

Функциональные модули: `accounts`, `transactions`, `goals`, `budgets`, `categories`, `payments`, `incomes`, `currencies`, `forecast`, `scenarios`, `data-transfer`, `security`, `settings`, `insights`, `debts`. Импорт, экспорт, копии и элементы восстановления относятся к `data-transfer`; блокировка и её настройки — к `security`; криптография и доступ к устройству — к `infrastructure`.

Формы и карточки принадлежат предметной функции, даже если используются на нескольких экранах: `GoalForm` и `GoalPreview` — в `features/goals/components/`, `TransactionRow` — в `features/transactions/components/`. Компонент без знаний о финансах и функциях приложения относится к `shared/ui`, чистая универсальная утилита — к `shared/lib`.

Создавайте `model/`, `lib/` и другие внутренние каталоги только для нужного содержимого. Не вводите новые провайдеры, независимые финансовые хранилища и дополнительные слои ради организации файлов.

## Зависимости и публичные интерфейсы

| Раздел           | Может импортировать                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------- |
| `shared`         | Только `shared`; без зависимостей от предметной модели                                                     |
| `domain`         | `domain` и чистые функции `shared/lib`, без React и платформенных API                                      |
| `infrastructure` | `infrastructure`, `domain`, `shared`                                                                       |
| `state`          | `state`, `domain`, `infrastructure`, `shared`                                                              |
| `features`       | Свой модуль, публичные интерфейсы других модулей `features`, `state`, `domain`, `infrastructure`, `shared` |
| `screens`        | Свой экран, публичные интерфейсы `features`, `state`, `domain`, `shared`                                   |
| `application`    | Все разделы для сборки приложения                                                                          |

- Между функциональными модулями не допускаются циклы. Из другого модуля, экрана или оболочки используйте публичный `index.ts` нужной функции; экспортируйте только то, что используется снаружи. Общий `index.ts` для всех `features` не создавайте.
- Внутри одного модуля используйте прямые относительные импорты, а не собственный `index.ts`. Доступ к финансовому состоянию снаружи `state/finance` идёт через `state/finance/index.ts`.
- Модульные тесты могут импортировать чистые функции из внутренних файлов, чтобы не загружать React Native через публичные UI-экспорты. Это исключение не распространяется на код приложения.
- `features` и `screens` могут использовать `import type` для контрактов из `src/application/navigation/types.ts`. Исполняемый код навигации остаётся в `application`.

[tests/architecture.test.ts](../tests/architecture.test.ts) проверяет размещение файлов, публичные импорты, отсутствие циклов для общих и нативных модулей и независимость финансового ядра от React и Expo. Проверки входят в `npm test`; не ослабляйте их ради обхода границ.

## Изменение финансового состояния

1. Новое финансовое действие сначала реализуйте в `src/domain/actions/`, затем подключите к `useFinanceActions` и форме. Единое состояние должно согласованно обновлять переводы, цели и валюты.
2. Действие принимает актуальный `FinanceState`, проверяет ограничения и возвращает новое состояние без изменения исходных объектов и массивов. При ошибке выбрасывает понятное исключение.
3. Вызывайте действие внутри `update(current => …)`: данные могли измениться после открытия формы. Общие проверки операции сохраняйте в `validateTransaction` / `appendTransaction`, чтобы ручной ввод и CSV соблюдали одни правила.
4. Форме оставьте черновик полей, преобразование ввода, показ ошибок и навигацию. Синхронные ошибки действий обрабатывайте через `useActionError`; файловым операциям нужна собственная асинхронная обработка.

Расчёты `domain` не обращаются к React, DOM, нативным API и хранилищу. Если результат зависит от времени, передавайте дату явно в расчёт и тест.

## Композиция приложения

Сохраняйте разделение UI по отдельным файлам. `Application` и экраны преимущественно собирают дочерние компоненты; предметная функция целиком не переносится в файл экрана.

Порядок в [AppProviders.tsx](../src/application/providers/AppProviders.tsx): `SecurityProvider` → `FinanceProvider` → `ReminderProvider` → `ExchangeRateProvider`. Реализации находятся соответственно в `features/security/model/`, `state/finance/`, `features/payments/model/`, `features/currencies/model/`. Изменение порядка требует проверки загрузки под блокировкой и планирования уведомлений.

Напоминания сохраняют это разделение: [domain/reminders.ts](../src/domain/reminders.ts) вычисляет даты и идентичность событий; [reminderSynchronizer.ts](../src/infrastructure/notifications/reminderSynchronizer.ts) управляет последовательностью чтения, отмены, планирования и очистки через переданные порты. Только `notifications.native.ts` обращается к Expo Notifications. Итоговый статус сверяется с фактически прочитанными триггерами через `notificationTrigger.ts`; результат не подтверждает доставку ОС. `ReminderProvider` связывает отображаемый результат с текущими состоянием, профилем и запросом, а `ReminderQueueStatus` показывает его внутри настроек. Финансовое состояние и порядок провайдеров от работы очереди не меняются.

Новые окна подключайте через `src/application/navigation/types.ts`, `src/application/shell/AppSheet.tsx` и `src/application/shell/SheetContent.tsx`, сохраняя существующий механизм навигации.

Удаление профиля и полный сброс координирует `Application`: `FinanceProvider` блокирует изменения и завершает очередь записи, затем передаёт подтверждённый запрос через callback `onDeleteData`. Оболочка размонтирует провайдеры, дожидается операций черновиков и обучения, очищает кэш хранилищ и выполняет журналируемый протокол `infrastructure/storage/dataDeletion.ts`. Пока удаление не закончено, финансовый интерфейс не монтируется. Прерванная операция продолжается перед обычной загрузкой; порядок существующих провайдеров сохранён.
