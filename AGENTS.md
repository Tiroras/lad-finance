# Инструкции для работы над «Ладом»

## Проект

«Лад» — приложение для личных финансов на React Native / Expo для iOS и Android. Web служит предпросмотром общего интерфейса и средой браузерных проверок. Интерфейс и документация — на русском, идентификаторы в коде — на английском.

- Учёт работает локально. Сервер, банковские подключения, облачная синхронизация и реальные списания сейчас отсутствуют.
- Стек: Expo SDK 57, React Native, React, TypeScript со строгой проверкой типов. Версии зависимостей сверяй с `package.json` и `package-lock.json`, Node.js — с `.nvmrc`.
- Перед изменением Expo API, нативных зависимостей или конфигурации сборки прочитай [документацию именно SDK 57](https://docs.expo.dev/versions/v57.0.0/) и нужного модуля. Для правок чистых расчётов и документации без этих изменений отдельное чтение Expo не требуется.
- Используй npm и существующий lock-файл; для совместимых нативных зависимостей — `npx expo install <package>`.
- Перед изменениями прочитай относящиеся к задаче код, тесты и документацию. Сохраняй незакоммиченные изменения пользователя и результаты предыдущих задач.

## Архитектура и границы ответственности

Перед изменением кода приложения прочитай [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md): там заданы размещение файлов, разрешённые зависимости, исключения для тестов и типов навигации, порядок провайдеров и подключение окон.

- Сохраняй структуру по функциональным модулям: `application` и `screens` собирают интерфейс, `features` содержат предметные компоненты, `domain` — финансовые правила, `state/finance` — единое состояние, `infrastructure` — платформенные адаптеры, `shared` — универсальный код.
- Внешние потребители используют публичные `features/<feature>/index.ts` и `state/finance/index.ts`; внутри модуля — прямые относительные импорты. Не допускай циклов и не ослабляй `tests/architecture.test.ts` ради обхода границ.
- Финансовые изменения из UI проводи через `useFinanceActions` и `src/domain/actions/`. Действие проверяет актуальное состояние внутри `update(current => …)` и возвращает новое, не изменяя исходные объекты. Переводы, цели и валюты обновляются согласованно.
- Расчёты в `domain` работают без React, DOM, платформенных API и хранилища; дату передавай явно. Общие проверки операции в `validateTransaction` / `appendTransaction` должны одинаково защищать ручной ввод и CSV.

## Финансовые правила

- Деньги хранятся в целых минимальных единицах валюты: JPY — 0, KWD — 3, остальные поддерживаемые валюты — 2 десятичных знака. Передавай правильный код в `parseMoney`, `moneyInput`, `money`; общие суммы показывай через `useMoney` в основной валюте. Используй `convertMoney` с целочисленным округлением; отсутствие курса — ошибка.
- Валюты счетов, целей и действующих планов неизменяемы. Сводки текущих остатков и прогноз используют текущие курсы; история доходов/расходов — сохранённый `baseAmount`. Редактирование названия не обновляет оценку. Ручной курс сохраняет приоритет при сетевом обновлении.
- В валютном переводе `amount` — списание, `toAmount` — зачисление. Взнос в цель учитывай по сумме зачисления; проверяй обеспеченность целей накоплениями отдельно для каждой валюты. Основную валюту меняй только через общее действие пересчёта бюджетов, истории и сценариев.
- Даты — локальные календарные строки `YYYY-MM-DD`. Используй `localDate`, `shiftDate`, `shiftMonth`, `dateInMonth`; не получай локальную дату через обрезку UTC-строки `toISOString()`.
- В коротком месяце 29–31-е число ограничивается последним днём месяца. Учитывай границы месяца, года и високосный февраль.
- Остатки счетов вычисляются по начальному остатку, фактическим операциям и датированным корректировкам. Корректировки не являются доходом или расходом и не переписывают начальный остаток; изменение денежных записей инвалидирует соответствующие сверки. Планируемые доходы, счета и сценарии сами по себе не создают операции.
- Перевод в одной валюте сохраняет общую сумму денег; при обмене учитываются две фактические суммы. Переводы не входят в доходы/расходы. Пополнение цели — перевод с повседневного счёта на накопительный, ограниченный оставшейся суммой цели.
- Накопительные счета исключаются из доступных для трат денег. Средства, закреплённые за целями, должны оставаться обеспечены накоплениями при переводе, изменении и удалении операций или корректировке счёта.
- Идентичность события — план, версия условий и исходный ключ: у прежнего ежемесячного плана месяц, у разового дохода `once`, у графиков day/week/month/year полная дата. Перенос дохода меняет ожидаемую дату отдельно; пропуски, ранняя оплата, ожидания, напоминания и сценарии сохраняют исходную идентичность.
- Привязка уже записанного расхода/дохода к плану не меняет баланс повторно. Удаление плана сохраняет фактические операции и очищает связанные ссылки.
- Условия планов сохраняй версиями с непересекающимися действующими интервалами; новые условия начинаются не раньше завтра. Остановка повторений с завтра сохраняет возникшие обязательства, возобновление сегодня использует прежние условия без заполнения паузы. Не изменяй уже отмеченные будущие события и не создавай неизвестные старые обязательства при чтении прежних данных. Подробности — в [docs/FORECAST.md](docs/FORECAST.md#история-условий-и-отдельные-поступления).
- Прогноз считает остатки на конец дня по повседневным счетам; горизонт включает сегодня. Повседневные расходы добавляются с завтрашнего дня, выполненные взносы и полученные доходы повторно не учитываются.
- Резерв в прогнозе — порог, в расчёте «Можно потратить» — вычитаемая сумма. Не смешивай эти модели и не вычитай бюджеты категорий повторно.
- Подкатегории делят бюджет основной категории. Агрегация расходов не должна считать их дважды. Архив сохраняет историю и действующие платежи; новые ручные операции и автоматический выбор CSV используют активные категории.
- Сценарий хранит условия отдельно от реального плана и пересчитывается от актуального учёта. Просроченные платежи не переписываются новой ценой.
- Максимальная покупка должна сохранять резерв на всём выбранном горизонте, включая обязательства после даты покупки. При нарушении резерва в базовом прогнозе не обещай безопасную дату.
- Для статистики, бюджетов и фильтров используй `expenseContributions` и `transactionIncomeAmount`: части покупки суммируются точно, возвраты уменьшают расходы на дату зачисления, движения основной суммы долга исключены из обычных доходов/расходов. Не заменяй это суммой по одному `transaction.type`.
- Кредитный лимит не входит в собственные деньги. Погашение карты — перевод; введённый оставшийся платёж уменьшается последующими переводами, а долги со сроком входят в прогноз. Выданный долг не обещает будущий надёжный доход.
- Бюджетные периоды и переносы рассчитываются в `domain/budgets.ts`, отдельно от месячной аналитики. Новая версия графика начинается на ближайшей будущей границе старого периода; перенос на границе определяется прежними правилами один раз. Закрытые периоды сохраняют условия; положительный перенос и перерасход независимы. Подробности — в [docs/BUDGETS.md](docs/BUDGETS.md).
- «Можно потратить» использует неполученный план дохода (или явно объяснённый резервный день из профиля), не прибавляет его к фактическим деньгам и проверяет дальнейший прогноз без повторного вычитания резервов.
- Симулятор должен оставаться чистым расчётом: смена суммы, даты и горизонта не изменяет счета, планы или историю.

Полные правила прогноза: [docs/FORECAST.md](docs/FORECAST.md). Базовый расчёт доступных денег: [README.md](README.md#как-считаются-деньги).

## Хранение, импорт и защита

- При изменении `FinanceState` согласованно обновляй типы, действия, чтение/проверку JSON и нужные начальные значения. Сохраняй чтение старых данных: новые необязательные поля обрабатывай с явными значениями по умолчанию, изменение обязательного формата сопровождай миграцией.
- JSON-копии проходят через `src/domain/backup.ts`. Проверяй ссылки, уникальность записей, ограничения сумм и совместимость старых копий.
- CSV добавляет выбранные операции одним обновлением после проверки всего пакета. Ошибка не должна оставлять частичный импорт; сохраняй поиск повторов и идентификаторы импорта.
- Восстановление и сброс в интерфейсе требуют предусмотренного подтверждения пользователя. Ошибка чтения не должна автоматически заменять данные пустым учётом или демоданными.
- Финансовый формат 7 хранит графики целей, циклы и освобождения годовых фондов, даты подтверждения и напоминания об обновлении кредитных условий; формат 6 — историю условий планов и изменения отдельных поступлений, 5 — статусы операций и архив счетов. Чтение 1–4 сохраняет прежнюю нормализацию в 4, чтение 5–6 не добавляет новую историю или поля. Новая семантика повышает формат действием; последующие действия его не понижают. Отсутствующая валюта прежних записей означает RUB. Версии конвертов шифрования независимы от финансового JSON.
- Нативные данные шифруются AES-GCM, ключ хранится отдельно в SecureStore. Сохраняй проверку новой зашифрованной записи до удаления старых данных при миграции.
- Переносимая `.ladbackup` использует отдельный пароль, фиксированные проверяемые параметры PBKDF2-SHA256 и AES-256-GCM. Не экспортируй ключ устройства и не сохраняй пароль; неверный пароль не должен менять хранилище. Для случайных байтов используй криптографический генератор без отладочного fallback.
- Web-хранилище и экспорт JSON не зашифрованы. Не приписывай им свойства нативного хранилища.
- Ключи, токены и личные финансовые записи не должны попадать в логи, тестовые фикстуры, снимки и коммиты. Для примеров используй демоданные.
- Доступ к платформенным API изолируй в адаптерах; учитывай различия `.native.ts` и `.ts`. Блокировка должна сохранять черновик формы и закрывать финансовый интерфейс при уходе в фон.

Валютные правила: [docs/CURRENCIES.md](docs/CURRENCIES.md).

Подробнее: [docs/CSV_IMPORT.md](docs/CSV_IMPORT.md), [docs/SECURITY.md](docs/SECURITY.md).

## Стиль и интерфейс

- Используй функциональные компоненты с типизированными props и существующие соглашения файлов. Для компонентов и функций — именованные экспорты; сохраняй существующие `default export` точек входа `App.tsx` и `src/application/Application.tsx`. Компоненты — `PascalCase`, хуки — `use…`.
- Предпочитай уже установленные библиотеки. Новую зависимость добавляй при необходимости задачи, учитывая размер приложения и совместимость с Expo.
- Переиспользуй `Txt`, `Button`, `Field`, `Card`, `Notice`, `Segments` и другие компоненты из `src/shared/ui/`. Цвета и шрифты бери из `C` и `font` в `src/shared/ui/theme.ts`.
- Сохраняй русский интерфейс, явную валюту сумм и локальный формат дат, доступные подписи и роли кнопок/полей. Сообщение об ошибке должно объяснять, что исправить.
- Общий интерфейс строится на React Native. DOM и браузерное хранилище допустимы в веб-адаптерах и браузерных инструментах, а не в общих экранах или расчётах.
- Проверяй узкий экран, перенос длинных названий и кнопок, прокрутку, Safe Area и клавиатуру. Ориентиры веб-проверок: 320, 390 и 1440 px.
- Форматируй изменённые файлы через Prettier. Не запускай массовое форматирование всего проекта ради локальной правки.

## Запуск и проверка изменений

Команды выполняются из корня; установка зависимостей — `npm ci`. Запуск, режимы и подготовка окружения описаны в [README.md](README.md#запуск). Перед тестированием прочитай относящийся к способу запуска раздел [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md).

```sh
npm start                 # Expo dev server
npm run ios               # iOS Simulator при установленном Xcode
npm run android           # Android-эмулятор или подключённое устройство
npm run web               # веб-предпросмотр
npm run typecheck         # TypeScript
npm test                  # модульные и архитектурные проверки
npm run test:e2e           # Playwright во всех трёх режимах
npm run build             # экспорт JS и ресурсов iOS, Android, Web
npx expo install --check  # совместимость зависимостей Expo
```

Выбирай проверки по затронутому поведению. Если изменение подходит под несколько строк, объединяй их требования; полный набор из последней строки нужен при завершении существенной функции, а не после каждой промежуточной правки.

| Изменение                                             | Проверки                                                                                                                           |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Только документация                                   | Команды, ссылки и якоря, Prettier, `git diff --check`                                                                              |
| Финансовые правила, действия, импорт, формат хранения | `npm run typecheck`, `npm test`, проверки изменённого поведения и значимых границ; для финансового бага — воспроизводящий его тест |
| Формы, навигация, пользовательские сценарии           | TypeScript, соответствующие Playwright-сценарии, визуальная проверка затронутых экранов                                            |
| Платформенные адаптеры, нативные зависимости, сборка  | TypeScript, связанные тесты, `npx expo install --check`, экспорт трёх платформ; системное поведение — на устройстве                |
| Завершённая существенная функция в нескольких слоях   | TypeScript, модульные тесты, весь Playwright и экспорт трёх платформ                                                               |

- Выбирай режим до проверки и указывай его в результате: default, Demo или Fresh. Fresh удаляет локальные данные всех профилей и допустим только с изолированными тестовыми данными; для проверки сохранения после перезапуска используй default или Demo без очистки.
- `npm run build` экспортирует JS и ресурсы, не создаёт APK/IPA. Браузерные тесты не подтверждают нативную биометрию, Keychain/Keystore, клавиатуру или уведомления.
- После успешных проверок повторяй их при новых изменениях или найденной проблеме. Документальная правка не требует полного прогона приложения.

## Агенты

- Для независимого ревью выбирай нужные роли по [docs/REVIEW_AGENTS.md](docs/REVIEW_AGENTS.md): `finance_reviewer` — финансовые правила, `ux_reviewer` — пользовательские сценарии, `code_reviewer` — качество реализации. Простой правке не нужен весь состав. Основной агент проверяет доказательства, объединяет повторы и отделяет дефекты от необязательных улучшений.
- Для отдельной задачи документации доступен `docs_agent` по [docs/DOCS_AGENT.md](docs/DOCS_AGENT.md); небольшую сопутствующую правку выполняет основной агент.

## Документация и завершение задачи

- Перед изменением пользовательского поведения прочитай затронутый раздел [docs/FEATURES_CURRENT.md](docs/FEATURES_CURRENT.md). В той же задаче обновляй обзор и тематические документы, если меняются функция, режим запуска, формат данных, защита или ограничение. Назначение документов и правила актуализации — в [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md#актуализация-документации).
- При работе над обучением сначала прочитай [docs/LEARNING_TOUR.md](docs/LEARNING_TOUR.md) и код. Согласованно обновляй сценарий, реализацию и проверки; сохраняй прохождение через настоящие экраны.
- В отчёт попадают только фактически выполненные проверки. Различай вывод по коду, модульные тесты, браузер, экспорт ресурсов, эмулятор и физическое устройство; не приписывай исторический прогон текущей версии и не выдумывай SHA или замеры. Результаты — в [docs/VERIFICATION.md](docs/VERIFICATION.md) и связанных отчётах, без изменчивого числа тестов в `AGENTS.md`.
- Для задач из [очереди follow-up](docs/tasks/2026-10-06-follow-up/README.md) сначала читай индекс, карточку, зависимости и связанные `analysis/`. Соблюдай указанные там порядок, уточнения объёма и смысл статусов; обновляй карточку и индекс вместе по [правилам ведения задач](docs/DEVELOPMENT.md#ведение-задач). Готовый анализ не означает внедрение функции.
- Снимки создавай по [правилам артефактов](docs/DEVELOPMENT.md#снимки-и-артефакты); не добавляй генерируемые каталоги в коммит.
- Перед завершением просмотри свой diff и выполни `git diff --check`. В ответе укажи результат, способ открыть новую функцию, выполненные проверки и оставшиеся ограничения, если они есть.
