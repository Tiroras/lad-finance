## Проект

«Лад» — приложение для личных финансов на React Native / Expo для iOS и Android. Web служит предпросмотром общего интерфейса и средой браузерных проверок. Интерфейс и документация — на русском, идентификаторы в коде — на английском.

- Основные функции: операции, счета в разных валютах, автоматические и ручные курсы, свои категории и подкатегории, бюджеты, цели, регулярные платежи, импорт/экспорт CSV, прогноз на 30/60/90 дней, планировщик покупки, сохранённые сценарии и переносимые копии с паролем.
- Учёт работает локально. Сервер, банковские подключения, облачная синхронизация и реальные списания сейчас отсутствуют.
- Стек: Expo SDK 57, React Native, React, TypeScript со строгой проверкой типов. Версии зависимостей сверяй с `package.json` и `package-lock.json`, Node.js — с `.nvmrc`.
- Используй npm и существующий lock-файл. Для совместимых нативных зависимостей используй `npx expo install <package>` и документацию нужного модуля для SDK 57.
- Перед изменениями прочитай относящиеся к задаче код, тесты и документацию. Сохраняй незакоммиченные изменения пользователя и результаты предыдущих задач.

## Архитектура и границы ответственности

Структура по функциональным модулям обязательна для дальнейших изменений. Перед созданием файла определи его ответственность по таблице; расширяй соответствующий модуль. Не возвращай общие каталоги `src/forms/`, `src/hooks/`, `src/services/`, `src/ui/`, `src/security/` или `src/navigation/` и отдельные `src/Application.tsx`, `src/store.tsx`, `src/backup.ts`.

- Форму и карточку размещай по предметной функции, даже если они используются на нескольких экранах. Например, `GoalForm` и `GoalPreview` принадлежат `features/goals/components/`, а `TransactionRow` — `features/transactions/components/`.

- Создавай `model/`, `lib/` и другие внутренние каталоги только для нужного содержимого. Новые провайдеры, независимые финансовые хранилища и дополнительные слои ради организации файлов не нужны.

- Внутри одного модуля используй прямые относительные импорты, а не собственный `index.ts`. Доступ к финансовому состоянию снаружи `state/finance` предоставляй через `state/finance/index.ts`.
- Модульные тесты могут импортировать проверяемые чистые функции напрямую из внутренних файлов, чтобы не загружать React Native через публичные UI-экспорты. Это исключение относится к тестам, а не к коду приложения.
- Допускается узкое исключение: `features` и `screens` могут использовать `import type` для контрактов из `src/application/navigation/types.ts`. Исполняемый код навигации остаётся в `application`.
- Архитектурные границы проверяются в `tests/architecture.test.ts` при `npm test`: размещение файлов, публичные импорты, отсутствие циклов для общих и нативных модулей, независимость финансового ядра от React и Expo. При добавлении файла соблюдай эти проверки; не ослабляй их ради обхода границ.

- Сохраняй разделение UI по отдельным файлам. `Application` и компоненты экранов должны преимущественно собирать дочерние компоненты, а не содержать целую функцию приложения в одном файле.
- Финансовые изменения из UI проводи через `useFinanceActions` из `src/state/finance/`. Новое действие сначала реализуй в `src/domain/actions/`, затем подключи в хук и форму. Финансовое состояние остаётся единым: переводы, цели и валюты обновляются согласованно.
- Действия принимают актуальный `FinanceState`, проверяют ограничения и возвращают новое состояние. При ошибке выбрасывают понятное исключение; исходные объекты и массивы не изменяют.
- Проверяй действие внутри `update(current => …)`: данные могли измениться после открытия формы. Сохраняй проверки общей операции в `validateTransaction` / `appendTransaction`, чтобы CSV и ручной ввод соблюдали одни правила.
- Формы отвечают за черновик полей, преобразование ввода, показ ошибок и навигацию. Синхронные ошибки действий обрабатывай через `useActionError`; файловым операциям нужна собственная асинхронная обработка.
- Расчёты в `src/domain/` должны работать без React, DOM, нативных API и доступа к хранилищу. Передавай дату явно в расчёты и тесты, когда результат зависит от времени.
- Сохраняй порядок провайдеров в `src/application/providers/AppProviders.tsx`: `SecurityProvider` → `FinanceProvider` → `ReminderProvider` → `ExchangeRateProvider`. Их реализации находятся соответственно в `features/security/model/`, `state/finance/`, `features/payments/model/`, `features/currencies/model/`. Изменения порядка требуют проверки загрузки под блокировкой и планирования уведомлений.
- Новые окна подключай через `src/application/navigation/types.ts`, `src/application/shell/AppSheet.tsx` и `src/application/shell/SheetContent.tsx`; используй существующий механизм навигации.

## Финансовые правила

- Деньги хранятся в целых минимальных единицах валюты: JPY — 0, KWD — 3, остальные поддерживаемые валюты — 2 десятичных знака. Передавай правильный код в `parseMoney`, `moneyInput`, `money`; общие суммы показывай через `useMoney` в основной валюте. Используй `convertMoney` с целочисленным округлением; отсутствие курса — ошибка.
- Валюты счетов, целей и действующих планов неизменяемы. Сводки текущих остатков и прогноз используют текущие курсы; история доходов/расходов — сохранённый `baseAmount`. Редактирование названия не обновляет оценку. Ручной курс сохраняет приоритет при сетевом обновлении.
- В валютном переводе `amount` — списание, `toAmount` — зачисление. Взнос в цель учитывай по сумме зачисления; проверяй обеспеченность целей накоплениями отдельно для каждой валюты. Основную валюту меняй только через общее действие пересчёта бюджетов, истории и сценариев.
- Даты — локальные календарные строки `YYYY-MM-DD`. Используй `localDate`, `shiftDate`, `shiftMonth`, `dateInMonth`; не получай локальную дату через обрезку UTC-строки `toISOString()`.
- В коротком месяце 29–31-е число ограничивается последним днём месяца. Учитывай границы месяца, года и високосный февраль.
- Остатки счетов вычисляются по начальному остатку, фактическим операциям и датированным корректировкам. Корректировки не являются доходом или расходом и не переписывают начальный остаток; изменение денежных записей инвалидирует соответствующие сверки. Планируемые доходы, счета и сценарии сами по себе не создают операции.
- Перевод в одной валюте сохраняет общую сумму денег; при обмене учитываются две фактические суммы. Переводы не входят в доходы/расходы. Пополнение цели — перевод с повседневного счёта на накопительный, ограниченный оставшейся суммой цели.
- Накопительные счета исключаются из доступных для трат денег. Средства, закреплённые за целями, должны оставаться обеспечены накоплениями при переводе, изменении и удалении операций или корректировке счёта.
- Старые ежемесячные планы сохраняют идентичность по месяцу, разовый доход — по плану. Новые графики day/week/month/year с интервалом используют полную дату обязательства: несколько недельных событий одного месяца независимы. Пропуски, ранняя оплата, напоминания и сценарии используют ту же идентичность.
- Привязка уже записанного расхода/дохода к плану не меняет баланс повторно. Удаление плана сохраняет фактические операции и очищает связанные ссылки.
- Просрочки, пропуски, дата начала и исторические условия платежей должны сохранять смысл при редактировании. Не создавай старые обязательства при чтении прежнего формата данных.
- Прогноз считает остатки на конец дня по повседневным счетам; горизонт включает сегодня. Повседневные расходы добавляются с завтрашнего дня, выполненные взносы и полученные доходы повторно не учитываются.
- Резерв в прогнозе — порог, в расчёте «Можно потратить» — вычитаемая сумма. Не смешивай эти модели и не вычитай бюджеты категорий повторно.
- Подкатегории делят бюджет основной категории. Агрегация расходов не должна считать их дважды. Архив сохраняет историю и действующие платежи; новые ручные операции и автоматический выбор CSV используют активные категории.
- Сценарий хранит условия отдельно от реального плана и пересчитывается от актуального учёта. При сдвиге дохода сохраняй исходный месяц для проверки получения; просроченные платежи не переписываются новой ценой.
- Максимальная покупка должна сохранять резерв на всём выбранном горизонте, включая обязательства после даты покупки. При нарушении резерва в базовом прогнозе не обещай безопасную дату.
- Для статистики, бюджетов и фильтров используй `expenseContributions` и `transactionIncomeAmount`: части покупки суммируются точно, возвраты уменьшают расходы на дату зачисления, движения основной суммы долга исключены из обычных доходов/расходов. Не заменяй это суммой по одному `transaction.type`.
- Кредитный лимит не входит в собственные деньги. Погашение карты — перевод; введённый оставшийся платёж уменьшается последующими переводами, а долги со сроком входят в прогноз. Выданный долг не обещает будущий надёжный доход.
- Бюджетные периоды и переносы рассчитываются в `domain/budgets.ts`, отдельно от месячной аналитики. Новые лимиты сохраняют закрытые периоды; положительный перенос и перерасход независимы.
- «Можно потратить» использует неполученный план дохода (или явно объяснённый резервный день из профиля), не прибавляет его к фактическим деньгам и проверяет дальнейший прогноз без повторного вычитания резервов.
- Симулятор должен оставаться чистым расчётом: смена суммы, даты и горизонта не изменяет счета, планы или историю.

Полные правила прогноза: [docs/FORECAST.md](docs/FORECAST.md). Базовый расчёт доступных денег: [README.md](README.md#как-считаются-деньги).

## Хранение, импорт и защита

- При изменении `FinanceState` согласованно обновляй типы, действия, чтение/проверку JSON и нужные начальные значения. Сохраняй чтение старых данных: новые необязательные поля обрабатывай с явными значениями по умолчанию, изменение обязательного формата сопровождай миграцией.
- JSON-копии проходят через `src/domain/backup.ts`. Проверяй ссылки, уникальность записей, ограничения сумм и совместимость старых копий.
- CSV добавляет выбранные операции одним обновлением после проверки всего пакета. Ошибка не должна оставлять частичный импорт; сохраняй поиск повторов и идентификаторы импорта.
- Восстановление и сброс в интерфейсе требуют предусмотренного подтверждения пользователя. Ошибка чтения не должна автоматически заменять данные пустым учётом или демоданными.
- Финансовый формат версии 4 читает версии 1, 2 и 3 с миграцией; отсутствующие валюты прежних записей означают RUB. Версии конвертов шифрования независимы от версии финансового JSON.
- Нативные данные шифруются AES-GCM, ключ хранится отдельно в SecureStore. Сохраняй проверку новой зашифрованной записи до удаления старых данных при миграции.
- Переносимая `.ladbackup` использует отдельный пароль, фиксированные проверяемые параметры PBKDF2-SHA256 и AES-256-GCM. Не экспортируй ключ устройства и не сохраняй пароль; неверный пароль не должен менять хранилище. Для случайных байтов используй криптографический генератор без отладочного fallback.
- Web-хранилище и экспорт JSON не зашифрованы. Не приписывай им свойства нативного хранилища.
- Ключи, токены и личные финансовые записи не должны попадать в логи, тестовые фикстуры, снимки и коммиты. Для примеров используй демоданные.
- Доступ к платформенным API изолируй в адаптерах; учитывай различия `.native.ts` и `.ts`. Блокировка должна сохранять черновик формы и закрывать финансовый интерфейс при уходе в фон.

Валютные правила: [docs/CURRENCIES.md](docs/CURRENCIES.md).

Подробнее: [docs/CSV_IMPORT.md](docs/CSV_IMPORT.md), [docs/SECURITY.md](docs/SECURITY.md).

## Стиль и интерфейс

- Используй функциональные компоненты, именованные экспорты, типизированные props и существующие соглашения файлов. Компоненты — `PascalCase`, хуки — `use…`.
- Предпочитай уже установленные библиотеки. Новую зависимость добавляй при необходимости задачи, учитывая размер приложения и совместимость с Expo.
- Переиспользуй `Txt`, `Button`, `Field`, `Card`, `Notice`, `Segments` и другие компоненты из `src/shared/ui/`. Цвета и шрифты бери из `C` и `font` в `src/shared/ui/theme.ts`.
- Сохраняй русский интерфейс, явную валюту сумм и локальный формат дат, доступные подписи и роли кнопок/полей. Сообщение об ошибке должно объяснять, что исправить.
- Общий интерфейс строится на React Native. DOM и браузерное хранилище допустимы в веб-адаптерах и браузерных инструментах, а не в общих экранах или расчётах.
- Проверяй узкий экран, перенос длинных названий и кнопок, прокрутку, Safe Area и клавиатуру. Ориентиры веб-проверок: 320, 390 и 1440 px.
- Форматируй изменённые файлы через Prettier. Не запускай массовое форматирование всего проекта ради локальной правки.

## Запуск и проверка изменений

Команды выполняются из корня проекта. Для установки зафиксированных зависимостей используй `npm ci`.

```sh
npm start                  # Expo dev server
npm run ios                # iOS Simulator при установленном Xcode
npm run android            # Android-эмулятор или подключённое устройство
npm run web                # веб-предпросмотр
npm run typecheck          # TypeScript
npm test                   # node:test + tsx, tests/*.test.ts
npm run test:e2e            # Playwright, tests/e2e/
npm run build              # экспорт JS и ресурсов iOS, Android и Web
npx expo install --check   # совместимость зависимостей Expo
```

### Режимы запуска и сборки для тестов

В проекте три режима: **дефолтный**, **демо** и **фреш (Fresh)**. Перед проверкой выбирай режим по сценарию и указывай его в результатах тестирования.

| Режим     | Данные и поведение                                                                                                                                                                           | Для каких тестов                                                                |
| --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Дефолтный | Обе опции `EXPO_PUBLIC_ENABLE_DEMO` и `EXPO_PUBLIC_RESET_ON_START` выключены. Сохранённый учёт загружается; при первом входе создаётся пустой личный профиль.                                | Обычный личный учёт, сохранение данных между запусками, отсутствие демофункций. |
| Демо      | `EXPO_PUBLIC_ENABLE_DEMO=true`, очистка выключена. Доступен отдельный профиль «Демо» с начальными примерами финансовых данных.                                                               | Заполненные экраны, аналитика, прогноз и сценарии с готовыми примерами.         |
| Фреш      | `EXPO_PUBLIC_RESET_ON_START=true`, демо по умолчанию выключено. В режиме разработки каждый новый запуск JS или полный Reload очищает локальные данные всех профилей и открывает приветствие. | Первый вход, обучение, пустые состояния и первоначальная настройка профиля.     |

- Дефолтный: `npm start`, `npm run web`, `npm run build`; браузерные проверки — `npm run test:e2e:personal`.
- Демо: `npm run start:demo`, `npm run web:demo`, `npm run build:demo`; браузерные проверки — `npm run test:e2e:demo`. В тесте явно выбирай профиль «Демо»: включение опции не заполняет личный профиль и не пропускает приветствие.
- Фреш: `npm run start:fresh`, `npm run web:fresh`; браузерные проверки — `npm run test:e2e:fresh`. Используй изолированные тестовые данные: режим удаляет весь локальный учёт без резервной копии. Обычный Fast Refresh очистку не повторяет. В release-сборке Fresh отключён условием `__DEV__`; отдельной команды `build:fresh` нет.
- Проверяй значения обеих опций в окружении и `.env*`: команды запуска наследуют их. После смены режима перезапускай Metro и выполняй полный Reload; для готового приложения нужна пересборка. Демо можно совместить с Fresh явно, если сценарию нужен чистый запуск с доступным демопрофилем.
- `npm run test:e2e` последовательно проверяет все три режима. Для мобильных тестов `npm run test:mobile -- path/to/flow.yaml` собирает release с выключенной очисткой; замени путь существующим сценарием нужного режима. Демо включается через `EXPO_PUBLIC_ENABLE_DEMO=true npm run test:mobile -- path/to/flow.yaml`. Параметр `--no-build` использует режим уже установленной сборки и не переключает его. Fresh через эту release-команду не включается. Файл или папка сценариев обязательны: без пути команда завершается до подготовки SDK, эмулятора и сборки.

Подробнее: [запуск с нуля](README.md#запуск-с-нуля), [деморежим](README.md#деморежим-по-явной-опции).

### Выбор проверок

Выбирай проверки по изменению:

| Изменение                                                         | Проверки                                                                                                                      |
| ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Только документация                                               | Корректность команд, ссылок, форматирования и `git diff --check`                                                              |
| Финансовые правила, действия, импорт, формат хранения             | `npm run typecheck`, `npm test`; добавь проверки изменённого поведения и значимых границ                                      |
| Формы, навигация, пользовательские сценарии                       | TypeScript, соответствующие Playwright-сценарии, визуальная проверка затронутых экранов                                       |
| Платформенные адаптеры, нативные зависимости, конфигурация сборки | TypeScript, связанные тесты, `npx expo install --check`, экспорт всех платформ; системное поведение проверяется на устройстве |
| Завершённая функция, затрагивающая несколько слоёв                | TypeScript, модульные тесты, весь набор Playwright и экспорт трёх платформ                                                    |

- Для исправления финансового бага добавляй тест, воспроизводящий ошибку. Не подменяй расчёты в тесте копией реализации; проверяй наблюдаемое поведение, точные суммы, даты, сохранность данных и отсутствие повторного учёта.
- Для проверки дат фиксируй `today` в модульных тестах и часы браузера в Playwright. Используй изолированный браузерный контекст с тестовыми данными.
- Playwright использует `http://localhost:8087`, локаль `ru-RU` и часовой пояс `Europe/Samara`. Локально он может переиспользовать сервер; в CI запускает собственный. Не останавливай чужой сервер ради теста.
- При установленном Chrome: `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`. Иначе установи Chromium командой `npx playwright install chromium`.
- Для интерактивных нативных проверок используй Maestro MCP, если он подключён к Codex. Сначала получи список устройств и явно выбери нужный эмулятор; режим приложения выбери до проверки. Для актуальной Android release-сборки используй `npm run test:mobile -- path/to/flow.yaml` с существующим сценарием и его предусловиями; Fresh проверяй в режиме разработки. Воспроизводимые сценарии сохраняй в `tests/mobile/<mode>/`. Общего smoke нет; `tests/mobile/demo/refactoring.yaml` требует Demo, завершённого приветствия, локальной даты `2026-10-04` и подготовки по [плану](tests/mobile/plans/refactoring.md#реализованный-сценарий-и-подготовленная-сборка). Настройка подключения: [README.md](README.md#maestro-mcp-для-codex).
- Для запрошенного цикла Maestro-агентов используй проектные роли `maestro_planner`, `maestro_generator`, `maestro_healer` из `.codex/agents/` и [docs/MAESTRO_AGENTS.md](docs/MAESTRO_AGENTS.md). Передавай между ролями выбранные устройство, режим и тестовые данные; на одном эмуляторе выполняй этапы последовательно. Healer сохраняет смысл проверок и отличает дефект приложения от ошибки сценария.
- Переносимое окружение описано в [docs/DOCKER.md](docs/DOCKER.md): `docker compose run --rm android test path/to/flow.yaml` собирает приложение и запускает Maestro; укажи существующий файл или папку сценариев, `--mode demo` и `--mode fresh` выбирают режим. Без пути тестирование завершается до подключения к эмулятору и сборки. Maestro не обходит подпапки автоматически. `docker compose run --rm android build` только собирает APK без сценария, `doctor` проверяет устройство без сценария. Fresh использует debug и отдельный Metro; он очищает все профили на выбранном тестовом эмуляторе. Для общих проверок используй `docker compose run --rm tools npm run <команда>`. Эмулятор работает на компьютере, MCP видит пути проекта как `/workspace/`; не смешивай контейнерные и локальные пути и не запускай два теста на одном устройстве одновременно.
- Для изолированного экспорта без сети: `EXPO_OFFLINE=1 npx expo export --platform all --max-workers 2`. Проверка зависимостей в offline-режиме использует локальные сведения SDK.
- `npm run build` создаёт JS-пакеты и ресурсы, а не APK/IPA. Успешные браузерные тесты не подтверждают системную биометрию, Keychain/Keystore, клавиатуру или уведомления на телефоне.
- CI находится в `.github/workflows/ci.yml`: типы/модульные тесты/зависимости, экспорт, браузерные сценарии. Отдельной команды `lint` сейчас нет.
- После успешных проверок повторяй их при новых изменениях или найденной проблеме. Для правки документации полный прогон приложения не нужен.

- Генерируемые `dist/`, `.expo/`, `test-results/`, `playwright-report/`, `ios/`, `android/` исключены из Git. Не добавляй их в коммит как побочный результат проверки.
- Перед завершением просмотри свой diff и выполни `git diff --check`. В ответе кратко укажи результат, способ открыть новую функцию, выполненные проверки и оставшиеся ограничения, если они есть.
