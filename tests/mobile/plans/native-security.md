# A04: системная защита и перенос копии

План для [T01](../../../docs/tasks/2026-10-06-follow-up/01-native-reliability-performance.md). Результаты фиксируются отдельно в [A04-native-security.md](../../../docs/tasks/2026-10-06-follow-up/reports/A04-native-security.md): наличие YAML и выполнение Node-тестов не означают прохождения системных шагов.

## Стенд и данные

- Только отдельные тестовые устройства и профиль `A04-<дата>-<платформа>`. Режим **default**, обе переменные Demo/Fresh выключены; собственная release-сборка `app.lad.finance`, без Expo Go. Записать SHA исходников, SHA-256 APK/IPA, модель, ОС, сборку, дату устройства и версии Maestro/ADB.
- Не использовать личный Pixel_8. Локальный AVD `Lad_FirstRun_Test` имеет диск `test-results/learning-opt-in/avd/`, запускается явно на `emulator-5556`. Перед каждым сценарием сверить `adb -s emulator-5556 emu avd name`. Ни `clearState`, ни Fresh, ни `pm clear`, ни удаление приложения для подготовки не нужны.
- На физическом iPhone и Android отдельно подготовить системный код и биометрию. Использовать только публичный тестовый код; не записывать настоящий код или биометрические данные в отчёт. Перед потерей ключа нужен отдельный одноразовый стенд и проверенная переносимая копия.
- `node --import tsx tests/mobile/fixtures/a04-fixtures.ts <каталог-запуска>` создаёт JSON, `.ladbackup`, подменённый конверт и некорректный JSON. Без аргумента используется игнорируемый `test-results/t01/a04/fixtures/`; для повтора выбирать новый каталог, например `test-results/t01/a04/2026-10-15/fixtures-offline`, чтобы сохранить старые манифесты. Скрипт проверяет валидатор, расшифрование, неверный пароль и подмену. Автоматические курсы явно выключены (`exchange: { automatic: false, rates: {} }`), чтобы сетевое обновление не меняло эталон во время сравнения полного состояния. Пароль `A04-synthetic-2026` публичен и годится только для этого набора.
- Эталон: 3 операции, 3 счёта, 1 цель; карта **9 300 RUB**, наличные **0 RUB**, накопления **1 000 RUB**. Цель связана с переводом `a04-transfer`, её целевая сумма **2 000 RUB**. Контрольный день **2026-10-06**, сверяются общие остатки/вся история, а не текущий месяц. SHA-256 JSON хранится в `manifest.json`.
- До восстановления создать второй синтетический контрольный профиль с отличимым остатком и записать его канонический хеш. После восстановления вернуться в него и сверить хеш. Создание профиля и подтверждение замены допустимы только в выделенном тестовом учёте.
- Артефакты каждого запуска — отдельный каталог `test-results/t01/a04/<дата>/`; фиксировать `passed`, `failed` или `not-run`. У `failed` различать приложение, сценарий и окружение. Не считать незавершённый журнал успешным прогоном.

## Запуск автоматизированных фрагментов

Все команды запускаются из корня проекта. В командах ниже `maestro` и `adb` должны быть из зафиксированного SDK/Java окружения. Выбирать один YAML, а не весь каталог: фрагменты имеют разные ручные предусловия.

```sh
adb -s emulator-5556 emu avd name
maestro --device emulator-5556 test -e PROFILE_NAME=A04-20261015-Android tests/mobile/default/security/a04-create-profile.yaml
maestro --device emulator-5556 test tests/mobile/default/security/a04-android-restore.yaml
maestro --device emulator-5556 test tests/mobile/default/security/a04-cold-lock.yaml
```

`a04-create-profile.yaml` начинается с уже настроенного, разблокированного приложения и заканчивается в файловом меню. `a04-android-restore.yaml` требует видимый `a04-valid.ladbackup` в Android DocumentsUI; он проверяет неверный пароль, подтверждённое восстановление, повторный запуск и эталон. Фрагменты `a04-restore-password.yaml` и `a04-tampered-password.yaml` начинаются после ручного выбора соответствующего файла.

Для повтора из уже созданного тестового профиля использовать `a04-open-backup-picker.yaml`: он открывает picker без создания второго профиля и без очистки данных. Если Android Recent пуст, открыть **Show roots → Downloads** (для системного языка English), затем выбрать файл. При фоновых обновлениях Play Store можно временно выключить Wi-Fi/мобильные данные только выделенного AVD; восстановление локального файла работает без сети. Записать это условие в отчёт и вернуть сеть после завершения всех нативных проверок.

`a04-confirm-password.yaml` проверяет правильный пароль, подтверждение замены и остатки; основной `a04-restore-password.yaml` вызывает его после отрицательного случая. Фрагмент можно отдельно выполнить после выбора валидной копии, если отрицательный путь уже подтверждён. Ожидание 600 секунд введено после наблюдения примерно 354 секунд на перегруженном Android-эмуляторе; это ограничение тестового ожидания, не приемлемая скорость продукта. Ожидание исчезновения поля пароля отделено от прокрутки к подтверждению, чтобы расположение блока ниже экрана не выдавалось за незавершённое вычисление.

`a04-android-restore-json.yaml` готовит тот же финансовый эталон через открытый JSON для независимых тестов хранения/блокировки. Этот путь не подтверждает парольное восстановление. `a04-open-security.yaml` открывает настройки защиты из разблокированного главного экрана при выключенной блокировке.

На физических устройствах системные диалоги, ввод кода/биометрии, обзор последних приложений, перенос файла и выбор назначения выполняются **вручную**. Для выделенного Android 17 AVD добавлены `a04-android-pin-enable.yaml` / `a04-android-pin-unlock.yaml` с публичным тестовым системным PIN `260615`: они нажимают реальные кнопки Android System UI, без подмены адаптера аутентификации. PIN задаётся только на отдельном тестовом AVD и удаляется после выключения защиты приложения. Это проверяет fallback на код, а не сильную физическую биометрию. `a04-auth-background.yaml` проверяет отмену диалога при Home; поздний успешный callback он не инъецирует. Не заявлять защиту снимков по одному дереву доступности: отдельно осмотреть реальную системную карточку и результат захвата. Пример запуска общих фрагментов на iOS аналогичен, но `--device` должен содержать подтверждённый ID выделенного iPhone/симулятора.

`a04-android-pin-disable.yaml` проверяет отмену и подтверждение выключения защиты; только после его успешного окончания можно удалить тестовый системный PIN. `a04-android-share-return.yaml` начинает с настоящего получателя файла и проверяет блокировку/аутентификацию при возвращении в Лад.

Для Android-стенда без подходящего файлового назначения предусмотрен [изолированный тестовый получатель](../support/share-receiver/README.md). `a04-open-json-export.yaml` открывает настоящий Sharesheet, `a04-send-test-receiver.yaml` выбирает получателя и ждёт новый SUCCESS. Затем `pull.mjs` выгружает прочитанные внешним приложением байты с проверкой receipt/размера/SHA-256; после этого запускается полный `a04-fixtures.ts verify`. Каждый результат привязывать к новому `callbackStartedAtEpochMs` и шагам текущего Maestro-прогона, чтобы не засчитать старый receipt. ERROR не обходить повторным чтением cache или внутреннего файла Лада. `a04-create-password-export.yaml` создаёт `.ladbackup` именно через UI и заканчивается в Sharesheet; для переноса используется этот файл, а не конверт Node-генератора. `a04-transfer-target-setup.yaml` проходит первый запуск пустой установки без очистки данных.

## S01. Подготовка, отмена и успех включения защиты

1. Восстановить эталон в новый профиль, сверить остатки и всю историю. Экспортировать JSON; проверить `node --import tsx tests/mobile/fixtures/a04-fixtures.ts verify <файл>`.
2. Открыть «Профиль и настройки → Защита данных → Включить блокировку». Отменить настоящий системный диалог. Блокировка не включается; сообщение объясняет неподтверждённое изменение.
3. Повторить и подтвердить биометрией или кодом. Настройка включена; доступна кнопка «Заблокировать сейчас». Данные неизменны.
4. На отдельном стенде без настроенного кода проверить понятное сообщение о настройке кода/биометрии. Этот вариант не отменяет проверки сильной Android-биометрии на оборудованном устройстве.

## S02. Холодный запуск, отмена и фон во время аутентификации

1. Записать запуск внешней камерой или безопасной системной записью; выполнить `a04-cold-lock.yaml`. До подтверждения входа нет финансового интерфейса, включая краткую вспышку. YAML проверяет только установившийся экран и не доказывает отсутствие вспышки.
2. Нажать «Разблокировать Лад», отменить системный диалог и выполнить `a04-auth-cancelled.yaml`. Повторить с неудачной биометрией: данные закрыты, повтор доступен.
3. Начать аутентификацию, уйти на Home до её окончания, вернуться. Даже поздний успех старого диалога не открывает приложение; нужен новый вход. Фиксировать фактический порядок событий.
4. Успешно войти и сверить эталон. Повторить холодный запуск 3 раза на каждой платформе; зафиксировать каждый результат, не объединять iOS и Android.

## S03. Черновик, фон, обзор приложений и снимок

1. При включённой защите выполнить `a04-background-draft.yaml`: новая несохранённая операция **37 RUB**, название `A04 unsaved draft`, затем Home и возврат. Поля и деньги скрыты под экраном блокировки.
2. В фоне открыть системный обзор последних приложений. На iOS финансовое содержимое должно быть закрыто системной защитой предпросмотра. На Android карточка и снимок не раскрывают данные при активном `FLAG_SECURE`. Проверить вручную, при необходимости сфотографировать только синтетический экран внешней камерой.
3. На Android попытаться снять экран системной комбинацией кнопок: финансовое содержимое не сохраняется. Ошибка/чёрный снимок средств автоматизации сама по себе не доказывает блокировку всех путей. На iOS запрет обычных снимков приложением не заявлен; проверяется именно предпросмотр в переключателе приложений.
4. Вернуться, вручную разблокировать, выполнить `a04-draft-after-unlock.yaml`. Черновик и сумма сохранены. Закрыть форму без сохранения; эталон не изменился.
5. Выключение защиты также требует успешной системной проверки. Отмена её не выключает; после подтверждённого выключения проверить снятие системной защиты снимков/предпросмотра.

## S04. Файловое меню и повтор действия

1. Включить защиту, открыть «Данные и копии → Восстановить из файла». Пока открыт системный picker, уйти на Home и открыть обзор приложений. Финансовое содержимое приложения закрыто.
2. Вернуться, отменить picker, пройти проверку входа. Нет неподтверждённой замены, пустого учёта или дубликатов. Повторно открыть picker и выбрать валидную копию: предусмотренный пароль/предпросмотр доступен после входа.
3. Создать копию с паролем и открыть реальное системное меню обмена. Уйти в фон, вернуться и отменить меню. Приложение не обещает, что внешний файл сохранён: допустима отметка **подготовки** с просьбой убедиться в сохранении файла.
4. Повторить экспорт, выбрать тестовое файловое назначение и вручную подтвердить наличие файла. Проверить экспорт скриптом `verify`. После закрытия меню не должны накапливаться временные файлы приложения; проверку каталогов выполнять только в выделенном контейнере приложения.

## S05. Неверный пароль, подмена, ошибочный JSON

1. При здоровом эталоне выбрать валидную `.ladbackup`, ввести неправильный пароль. `a04-restore-password.yaml` проверяет ошибку и отсутствие кнопки замены, затем правильный пароль и восстановление. Для доказательства неизменности после отказа отдельно отменить ввод, экспортировать текущий JSON и выполнить `verify` **до** правильного восстановления.
2. Выбрать `a04-tampered.ladbackup`, выполнить `a04-tampered-password.yaml`. Повторно экспортировать JSON и выполнить `verify`; не ограничиваться сообщением «Данные не изменены».
3. Выбрать `a04-malformed.json`: понятная ошибка, нет подтверждения замены и автоматического пустого учёта. Повторно проверить текущий JSON и контрольный профиль.
4. Восстановить правильную копию, отменить подтверждение замены и снова сверить эталон. Только отдельное явное подтверждение может менять финансовые записи.

## S06. Перенос между устройствами

1. На устройстве A создать `.ladbackup` **через интерфейс приложения**, сохранить её в тестовое назначение и проверить скриптом `verify`.
2. Передать только этот файл на отдельное устройство B со своей установкой и новым тестовым профилем. Ключи SecureStore, каталог приложения и системную резервную копию не копировать.
3. Восстановить файл через настоящий picker, пароль и подтверждение; сверить 3 операции, ссылки цели, остатки, а затем канонический JSON скриптом `verify`. Перезапустить B и повторить сверку.
4. Сверить исходный профиль A и контрольные профили обоих устройств. Выполнить направления Android → iOS и iOS → Android отдельно. Перенос Node-файла на один эмулятор не считается этим сценарием.

## S07. Отсутствие локального ключа и восстановление

1. Только на выделенном одноразовом устройстве/контейнере с эталоном и заранее проверенной внешней копией остановить приложение. Сохранить хеш зашифрованного конверта, удалить **только ключ текущего тестового профиля** средствами тестового стенда; сохранить конверт и список профилей. В отчёте указать точный инструмент и селектор. Ключ не печатать и не экспортировать.
2. Запустить приложение. Ожидается экран ошибки чтения с восстановлением: отсутствуют автоматический пустой учёт, fallback к старому открытому JSON и молчаливая перезапись конверта.
3. Отменить picker/пароль и повторить запуск: ошибка сохраняется, хеш исходного конверта прежний. Неверный пароль/подмена также не меняют хранилище.
4. Выбрать правильную копию, ввести пароль, проверить предварительные данные и явно подтвердить восстановление. Новый ключ создаётся штатным путём. После перезапуска эталон читается; контрольный профиль неизменен.
5. Если платформа не даёт изолированно удалить ключ без удаления финансового конверта, этот системный случай **not-run**. Не заменять его переустановкой, удалением всего приложения, `pm clear`, потерей всех ключей или результатом Node-мока.

## Критерий завершения

В отчёте отдельно заполнить физические iOS, Android и вспомогательный эмулятор. A04 остаётся открытым при отсутствии хотя бы одной физической платформы или системного сценария. Подтверждённые адаптерные проверки полезны, но не закрывают пробелы Keychain/Keystore, жизненного цикла системного диалога и переноса между установками.
